# Sitemap, robots и Google Search Console

Актуально на 9 ноября 2026. Публичные файлы: [robots.txt](https://tamir.rs/robots.txt) и [sitemap.xml](https://tamir.rs/sitemap.xml). Источники реализации — `frontend/src/app/robots.ts`, `sitemap.ts`, общий SEO-код витрины `frontend/src/lib/seo.ts` и `backend/src/api/middlewares.ts`.

## Что включено в sitemap

- Обе главные: `/rs` и `/en`, без перенаправления в каталог.
- Локализованные страницы terms/privacy/cookies.
- Все доступные витрине SR-товары, а EN-товары — только с готовыми английскими названием/описанием и адресом.
- Непустые публичные категории с локализованными адресами и индексируемые страницы пагинации каталога/категорий.

Загрузка товаров проходит все страницы Store API, а не ограничивается первой сотней. Учитываются публикация, канал продаж и доступность записи витрине. Черновики не обязаны совпадать по количеству с sitemap. Новые доступные товары появляются без деплоя. `lastmod` товара берётся из корректного `updated_at`.

Первая страница общего `/rs/catalog` канонизирована на `/rs`, `/en/catalog` — на `/en`. Фильтры и сортировки не создают отдельные записи sitemap. Пары SR/EN связаны hreflang; для неготового EN-товара не публикуется ложная готовая альтернатива. [Критерии EN](LOCALIZATION.md).

## Индексация и ожидаемые исключения

| Ситуация в Search Console | Поведение проекта |
| --- | --- |
| Страница с переадресацией | Прежние категории/служебные URL ведут на текущий адрес. Старые товарные URL возвращают 404 без перенаправления |
| Вариант с canonical | `?v_id=...`, сортировка и фильтры указывают на основную страницу. Вариант товара при этом остаётся выбранным в интерфейсе |
| `noindex` | Кабинет, корзина, checkout, заказ, внутренний поиск, пустые категории и неготовые EN-карточки исключены намеренно; 404 также может содержать noindex |
| Google выбрал другой canonical | Проверьте конечный ответ, canonical/hreflang, внутренние ссылки и sitemap одного и того же URL; не отменяйте полезные redirects ради исчезновения строки отчёта |

`robots.txt` блокирует `/api/`. Приватные страницы доступны роботу для чтения `noindex, nofollow`, но это не заменяет авторизацию. Публичные главные, заполненные категории/товары и legal-страницы не имеют общего запрета индексации. `.woff2`, robots.txt и sitemap.xml — технические ресурсы, не товарные страницы для sitemap.

## Проверка и отправка

Один существующий ресурс Search Console для `tamir.rs`, охватывающий оба пути, обслуживает SR и EN; отдельный домен/ресурс только ради EN не нужен. Отправьте `https://tamir.rs/sitemap.xml` в разделе «Файлы Sitemap». Robots отдельно отправлять не требуется. Стендовые адреса в Search Console не отправляются и не добавляются: см. раздел «Стенд закрыт от поисковиков».

```bash
curl -fsS https://tamir.rs/robots.txt
curl -fsS https://tamir.rs/sitemap.xml
curl -I https://tamir.rs/rs
curl -I https://tamir.rs/en
```

Для проблемного товара проверяйте **точный URL**, конечный HTTP-статус, HTML canonical/hreflang/robots, HTTP `X-Robots-Tag` и дату последнего обхода. Используйте проверку опубликованной страницы в Search Console. Старый отчёт не обновляется в момент деплоя; отправка не гарантирует индексацию.

Если sitemap недоступен или неполон, проверьте `/health` backend, публикацию, связь с каналом publishable key, переводы и логи frontend. Не подменяйте ошибку API пустым успешным sitemap.

## Стенд закрыт от поисковиков

Стенд (`test.tamir.rs`, `test-api.tamir.rs`) работает тем же кодом, что и прод, поэтому закрытие держится не на отдельном конфиге, а на имени хоста: всё, что не входит в allow-list публичных прод-адресов (`SEARCHABLE_HOSTS` в `frontend/src/lib/seo.ts`, `SEARCHABLE_API_HOSTS` в `backend/src/api/middlewares.ts`), получает `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` на каждом ответе — включая redirects витрины, 404 витрины и служебные маршруты backend вроде `/health`. Три ответа на стенде, которыми приложение не управляет, добирает правило Cloudflare («Зазоры, которые закрывает правило Cloudflare»). Локальные адреса разработки (`localhost`, `*.localhost`, IPv4-литералы по HTTP) закрытием не затрагиваются.

На закрытом хосте `robots.txt` намеренно остаётся разрешающим (`Allow: /`, без строки `Sitemap:`), а `sitemap.xml` отдаёт пустой `<urlset>` без обращений к API. Причина: Google снимает URL с индекса, только когда может прочитать `noindex` в ответе, — `Disallow: /` в robots.txt как раз помешал бы роботу этот ответ увидеть. Ужесточать robots.txt имеет смысл лишь после того, как стендовые URL исчезнут из индекса; до этого это закрепило бы их в выдаче.

Публичные прод-хосты входят в ту же allow-list, поэтому деплой на прод для самого прода незаметен: `X-Robots-Tag` на `tamir.rs` и `api.tamir.rs` не появляется.

### Проверка закрытия

Проверяются заголовки ответов, а не только тело:

```bash
bash scripts/seo-headers-check.sh          # стенд, прод, robots, sitemap, canonical
SEO_STRICT=1 bash scripts/seo-headers-check.sh   # зазоры (строки `gap`) считаются провалом
```

Норма для исправного стенда и незадетого прода — `PASS=21 FAIL=0 GAP=0` (9 ответов стенда, 6 ответов прода, canonical `www`, robots и sitemap). Измерено 9 ноября 2026 после включения правила Cloudflare.

Скрипт обращается к тем же публичным адресам, что и поисковый робот, секретов не требует, только GET. Отдельные `curl`-проверки:

```bash
curl -sSI https://test.tamir.rs/rs | grep -i x-robots-tag
curl -sSI https://test.tamir.rs/ | grep -i x-robots-tag
curl -sSI https://test-api.tamir.rs/health | grep -i x-robots-tag
curl -fsS https://test.tamir.rs/robots.txt
curl -fsS https://test.tamir.rs/sitemap.xml
```

На проде (`tamir.rs`, `api.tamir.rs`) заголовка `X-Robots-Tag` быть не должно.

### Зазоры, которые закрывает правило Cloudflare (закрыты 9 ноября 2026)

Три ответа на стенде приложение не формирует, поэтому `X-Robots-Tag` в них не было:

| URL | Ответ | Причина |
| --- | --- | --- |
| `https://test-api.tamir.rs/app` | 200, HTML кабинета | Medusa раздаёт admin-статику раньше глобального middleware |
| `https://test-api.tamir.rs/store/products` | 400, JSON | `ensurePublishableApiKeyMiddleware` бросает ошибку до него |
| `https://youtrack.tamir.rs/*` | 200, HTML YouTrack | внешний трекер, кода которого в репозитории нет; хост в той же зоне Cloudflare |

Замена дефолтного `errorHandler` Medusa ради первых двух ответов трогает и прод, а YouTrack вообще не наш код, поэтому все три закрывает правило Cloudflare — Transform Rules → Transform Rule → Modify Response Header:

```
If: (http.host eq "test.tamir.rs" or http.host eq "test-api.tamir.rs" or http.host eq "youtrack.tamir.rs")
Then: Set header "X-Robots-Tag" = "noindex, nofollow, noarchive, nosnippet" (overwrite)
```

Правило действует после приложения и не меняет ни тело, ни статус ответа. Применено 9 ноября 2026 и проверено: `https://test-api.tamir.rs/app` отвечает 200 с заголовком, `https://test-api.tamir.rs/store/products` — 400 с заголовком, `https://youtrack.tamir.rs/login` — 200 с заголовком.

Координаты в Cloudflare (зона `tamir.rs`), чтобы не искать вслепую:

| | |
| --- | --- |
| Дашборд | Rules → Overview → тип `Modify Response Header` (`.../tamir.rs/rules/overview?type=http_response_headers_transform`) |
| Ruleset | `seo-noindex-staging`, id `7acf450c8daf42f4a34d012f5e96a77b`, phase `http_response_headers_transform` |
| Правило | id `2ffeeb55183f4f8aa40c73db45e49a08`, `enabled: true` |

Это entrypoint фазы, то есть единственные правила этой фазы в зоне; в API — `GET /zones/<zone>/rulesets/phases/http_response_headers_transform/entrypoint`. Правку вносить `PUT` на этот же entrypoint (повторный `POST` на `/rulesets` отдаёт `20217 exceeded maximum number of zone rulesets for phase`). В выражении только стендовые хосты — `tamir.rs`, `www.tamir.rs`, `api.tamir.rs` и `tamir.ua` под это правило добавлять нельзя: оно снимало бы индексацию с настоящего магазина.

### Факт обхода виден в аналитике Cloudflare, а не в панели Search Console

Отчёт Search Console догоняет недели, поэтому подтверждение берут из аналитики самой зоны: GraphQL дашборда `POST https://dash.cloudflare.com/api/v4/graphql` (не `api.cloudflare.com` — тот блокируется CORS из страницы дашборда), датасеты `httpRequestsAdaptive` и `httpRequestsAdaptiveGroups` у `zone`. `firewallEventsAdaptive` для этого не годится: на стендовых хостах событий WAF нет, запрос всегда пустой.

```graphql
query {
  viewer { zones(filter: { zoneTag: "<zone id>" }) {
    httpRequestsAdaptive(filter: {
      datetime_geq: "2026-11-09T09:27:00Z", datetime_lt: "2026-11-09T12:00:00Z",
      clientRequestHTTPHost_in: ["test.tamir.rs", "test-api.tamir.rs", "youtrack.tamir.rs"],
      verifiedBotCategory_in: ["Search Engine Crawler"]
    }, limit: 30) { datetime clientRequestHTTPHost clientRequestPath edgeResponseStatus userAgent }
  } }
}
```

Время задают только парой `datetime_geq`/`datetime_lt` внутри `filter`, фильтры плоские (`clientRequestHTTPHost_in`, `userAgent_like`), у датасета нет `edges`/`node` — это плоский список объектов. Поля `botScore` и `payPerCrawlStatus` этой зоне недоступны (`authz`).

Группировка за 6–9 ноября по той же зоне: Googlebot сделал 28 запросов `test.tamir.rs/robots.txt`, обошёл `/rs`, `/en`, `/rs/catalog`, `/cookies`, `/terms`, товарные страницы и статические чанки; `Googlebot-Image/1.0` сделал 68 запросов к `test-api.tamir.rs/static/rozetka-*.jpg` (больше сорока разных файлов) — то есть стендовые файлы уже попадали в поиск по картинкам, и заголовок нужен в том числе API-хосту. Отдельный обход `youtrack.tamir.rs` (YandexBot) — то самое основание добавить этот хост в правило Cloudflare.

Заголовок `X-Robots-Tag: noindex` в этих ответах ставили два слоя: приложение стенда — с релиза 09:27 UTC, правило зоны — с 10:16 UTC для `test.tamir.rs`/`test-api.tamir.rs` и с 10:23 UTC для `youtrack.tamir.rs` (версии ruleset видно через `GET /zones/<zone>/rulesets/<id>/versions`: 10:16:51, 10:17:29, 10:23:08). Поэтому обход `youtrack.tamir.rs` 8 ноября заголовка ещё не получал — это и стало основанием добавить хост в правило. По остальным строкам вывод такой: обход с `noindex` состоялся, осталась только перестройка индекса, и повторять запросы индексирования бессмысленно. Сама панель инспекции `https://test.tamir.rs/` в 10:35 UTC показывала старую запись — «URL есть в индексе Google», «Эта страница проиндексирована»; это ожидаемо, индекс перестраивается днями. Тем же запросом с `userAgent_like: "%Googlebot%"` удобно смотреть прод: видно, какие товарные адреса Google обходит и получает по ним `404`.

Порядок снятия: дождаться обхода, который увидит `noindex` (crawl-то открыт), затем «Удаления → Устаревший контент» для конкретных URL, после чего удалить отдельное свойство `test.tamir.rs` из Search Console и лишь тогда ужесточать его `robots.txt`. Подтверждение, что пошёл нужный обход: инспекция `https://test.tamir.rs/` показывает `307` и «Индексирование страницы запрещено тегом `noindex`» вместо старой версии страницы. Отчёт обновляется с задержкой; массовые запросы индексирования не ускоряют снятие.

### Дубли хостов

`www.tamir.rs` и `tamir.ua` входят в `SEARCHABLE_HOSTS` намеренно: они закрыты не `noindex`, а canonical — витрина строит canonical из `NEXT_PUBLIC_SITE_URL`, поэтому `https://www.tamir.rs/rs` отдаёт `<link rel="canonical" href="https://tamir.rs/rs"/>` и Google склеивает дубли без исключения страницы. В индексе сейчас один такой адрес: `https://www.tamir.rs/en/products/men-s-fine-knit-scarf-gray`. Измерено 9 ноября: и на главной, и на глубокой странице `www.tamir.rs` canonical уже ссылается на apex, поэтому принудительный `301 www → apex` — гигиена, а не условие закрытия. Это отдельное изменение прод-роутинга: перед ним сверяют, что правило не ломает переключение языка и уже работающий canonical.

Отдельный долг — 177 URL группы 404: прежние слаги переименованных товаров и `rozetka-*`-заглушки, а также обходимость адресов с `?page=` и `?v_id=`. Товарные перенаправления отключены решением владельца, поэтому вопрос о 301 для этих адресов остаётся за владельцем.

## Обновление внутренних ссылок — 12 октября 2026

Меню «Все товары», футер, ссылки возврата и сброса ведут на `/rs` / `/en`, совпадая с canonical первой страницы. Генератор пагинации возвращает на эту же главную при выборе первой страницы без фильтров и сортировки. Последующие страницы сохраняют `/catalog?page=N`, категории — собственные адреса. Старый `/catalog` остаётся доступным с canonical главной. Страница пагинации за пределами текущего числа товаров возвращает 404, а не пустой индексируемый 200; сбой backend не считается доказательством удаления страницы.

Обычная карточка ведёт на чистый адрес товара, если выбран его стандартный вариант. Явный выбор цвета или вариант, подходящий фильтру, сохраняет `v_id`, когда без него открылась бы другая вариация. В JSON-LD товара с единственным вариантом Offer URL совпадает с чистым адресом; у нескольких вариантов остаются конкретные selectable URL. Canonical всех вариантов по-прежнему указывает на товар. Цель — согласованные ссылки, а не принудительная индексация каждого параметра.

## Что делать при замене товара

| Ситуация | Действие |
| --- | --- |
| Тот же товар: меняются фото, цена, описание или перевод | Редактируйте существующую карточку, сохраняйте ID и URL |
| Товар временно закончился | Оставьте полезную опубликованную карточку с честным нулевым остатком; не удаляйте URL только из-за отсутствия на складе |
| Та же карточка получает новый адрес | По политике владельца старый товарный URL возвращает 404. EN-виджет сохраняет историю резерва адресов, но resolver её не обслуживает |
| Старый товар удалён, затем импортирован снова | Это новая карточка. Старые отличающиеся адреса возвращают 404, даже при совпадении модели поставщика |
| Товар удалён окончательно, подходящей замены нет | Корректный 404/410 допустим; уберите старую карточку из внутренних ссылок/sitemap, не перенаправляйте все ошибки на главную |

Не превращайте старую карточку шарфа в несвязанную карточку другого товара ради сохранения индексации: это также смешивает отзывы и товарную историю. Редактирование перевода, импорт и изменение URL — разные операции. Товарные перенаправления отключены по решению владельца. Не редактируйте служебные URL-таблицы произвольным SQL.

### Повторный импорт после удаления

Повторно импортированный товар считается новой карточкой. Resolver не ищет замену в soft-deleted товарах, не читает `rozetka_legacy_handle` и не обслуживает строки `tamir_product_url` с `is_current=false`. Он нужен только для текущего английского адреса опубликованного неудалённого товара; доступность каналу затем проверяет Store API.

Витрина принимает только текущий handle выбранного языка. Старые/чужие языковые адреса дают 404 с noindex, в том числе с `v_id`; перенаправления на другой товар или главную нет. Сбой API не маскируется под удаление. Переключатель языка использует актуальные SR/EN-ссылки.

Sitemap и внутренние ссылки строятся из текущих доступных товаров, без исторических URL. После удаления и импорта вручную редактировать sitemap не нужно. Если нынешний товар использует точно тот же URL, что прежний, этот действующий URL остаётся 200: один адрес нельзя одновременно обслуживать и считать удалённым. Текущие адреса специально не переименовываются.

Удаление старых публичных адресов не требует физического удаления истории заказов, отзывов или soft-deleted строк. Старые адреса постепенно исключаются из поиска после повторного обхода; записи 404 могут оставаться в Search Console и не означают поломку текущих карточек.

Строки «Страница с переадресацией» и «Вариант страницы с тегом canonical» для ожидаемых старых/параметрических адресов не требуют удаления защиты от дублей. Проверка исправления может не пройти, пока URL намеренно остаётся redirect/alternate; контролируйте индексацию конечной основной страницы. Robots, sitemap, favicon и шрифты не обязаны появляться в поисковой выдаче как страницы магазина. Отправка sitemap и запрос индексирования не дают гарантированного срока или включения в индекс.

Официальные пояснения Google: [отчёт об индексировании](https://support.google.com/webmasters/answer/7440203), [адреса интернет-магазина](https://developers.google.com/search/docs/specialty/ecommerce/designing-a-url-structure-for-ecommerce-sites), [удалённые и перемещённые страницы](https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors).
