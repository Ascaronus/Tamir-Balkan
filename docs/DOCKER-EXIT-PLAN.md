# План отказа от Docker в TAMIR

Дата: 20 октября 2026. Статус: **план; миграция не выполнена**.

## Цель и границы

Перенести PostgreSQL и Redis из контейнеров в системные службы Ubuntu на том же VPS. После проверки работы и завершения периода отката удалить зависимость проекта от Docker: на production, в инструкциях разработки и в CI. Сам документ ничего не устанавливает и не переключает.

Backend Medusa и frontend Next.js уже работают напрямую на VPS через PM2. Сохранить этот способ запуска; проверить запуск PM2 при загрузке через systemd. Переписывание приложений в самостоятельные systemd-unit-файлы не требуется для отказа от Docker и не входит в эту миграцию. Домены, HTTPS, товарные URL и языки SR/EN сохраняются.

## Подтверждённое исходное состояние

Источники: текущие файлы репозитория и вывод команд, предоставленный владельцем VPS 20 октября. Перед выполнением повторить инвентаризацию; этот документ не заменяет актуальную проверку сервера.

| Компонент | Сейчас | Цель |
| --- | --- | --- |
| ОС | Ubuntu 24.04 LTS по данным проекта; проверить на VPS | Та же ОС, без переустановки в рамках обычной миграции |
| PostgreSQL | Образ `postgres:16`, контейнер `tamir_balkan-postgres-1`, БД `medusa-v2` | PostgreSQL 16 из доверенного APT-репозитория, отдельный кластер под systemd |
| Файлы PostgreSQL | Compose-том `postgres_data`; фактическое имя и mount уточнить | Собственный каталог кластера на диске VPS, владелец `postgres` |
| Redis | Образ `redis:7`, версия 7.4.8 в присланном логе | Поддерживаемая исправленная версия Redis, проверенная с Medusa/ioredis, служба systemd |
| Порты на VPS | По последней проверке `127.0.0.1:5432` и `127.0.0.1:6379` | Сохранить эти адреса после переключения |
| Backend / frontend | PM2: `tamir-backend`, `tamir-frontend` | Те же приложения и механизм релизов |
| Исходники / релизы | `/root/tamir_balkan`, `/root/tamir-releases` | Сохранить пути и загрузки файлов |
| CI | `.github/workflows/verify.yml` поднимает `postgres:16` как service container | PostgreSQL 16 непосредственно на runner без контейнера |

В `backend/medusa-config.ts` Redis подключён через `projectConfig.redisUrl` для серверных сессий. Redis-модули кеша, очередей и workflow отдельно не объявлены. Перед отказом от переноса данных Redis проверить фактические ключи и все приложения-потребители: конфигурация могла измениться.

На VPS настроен `restart: unless-stopped` для Redis, но в проверенном `docker-compose.yml` ветки main этой строки нет. В Git оба порта уже ограничены loopback. `scripts/deploy-vps.sh` отказывается работать при локальных изменениях отслеживаемых файлов. До следующего деплоя согласовать серверную правку с Git, сохранив ограничение портов; не использовать принудительный сброс рабочего дерева.

## Условия безопасности до начала

В логе Redis обнаружены внешний клиент с командой `FLUSHALL`, многократные очистки, изменения репликации и отклонённые загрузки модулей. Точная причина SIGSEGV и масштаб доступа не установлены. Переход с Docker на systemd не устраняет последствия возможного проникновения.

- [ ] Сохранить полный crash report, журналы Redis/PostgreSQL, конфигурации контейнеров и временную шкалу в защищённое хранилище вне публичного Git. Сохранённый лог Redis на VPS: `/root/redis-incident-2026-10-20.log`, если команда сохранения была выполнена; наличие проверить.
- [ ] Проверить доступы к ОС, задачи cron, systemd-службы, SSH-ключи, расширения и роли PostgreSQL, изменённые файлы. Не считать отсутствие ошибок доказательством чистоты.
- [ ] Если обнаружен доступ к ОС или нельзя доверять серверу, изменить маршрут: новый чистый VPS и перенос проверенных данных. Не объявлять прежний VPS безопасным после одной смены способа запуска.
- [ ] Сменить слабый пароль БД, подготовить авторизацию Redis и проверить фактические JWT/COOKIE-секреты. Ротацию выполнять согласованно с backend; не возвращать скомпрометированные секреты при откате. Возможный сброс входов учитывать заранее.
- [ ] Не помещать пароли, `.env`, PM2 JSON, реальные дампы, ключи и содержимое пользовательских сессий в репозиторий или PR. Резервные копии таких файлов тоже содержат секреты.

## Этап 1. Инвентаризация и подготовка окна

- [ ] Зафиксировать точные версии серверов и клиентов, размер БД, свободное место и память. На время репетиции нужны ресурсы для двух экземпляров, дампов и восстановления.
- [ ] Зафиксировать volumes/mounts, все БД, роли, владельцев, расширения, encoding/locale, число товаров, вариантов, категорий, заказов и пользователей; согласовать контрольные SQL-запросы по фактической схеме.
- [ ] Выяснить активный release, cwd обоих PM2-процессов, источники `DATABASE_URL` и `REDIS_URL`, файлы загрузок `static`/`private-static`, фоновые задания и внешних писателей в БД.
- [ ] Проверить другие контейнеры, пользователей Docker, сторонние агенты и зависимости от containerd. Не удалять общий runtime, если он нужен другому приложению.
- [ ] Приостановить автоматические production-деплои на период миграции, дождаться уже запущенных workflow и блокировки `/root/tamir-deploy.lock`. Не обходить блокировку параллельным запуском скриптов.
- [ ] Определить окно обслуживания по измеренной длительности восстановления. Обещание нулевого простоя не давать. Цель: не потерять подтверждённые записи, сделанные до остановки записи; допустимый простой согласовать до переключения.

## Этап 2. Резервная копия и репетиция восстановления

Существующий `/root/tamir-db-before-port-fix.dump` успешно прошёл чтение оглавления. Это не проверка полного восстановления и не копия гарантированно чистого состояния до инцидента.

- [ ] Создать новый custom-format дамп PostgreSQL 16, отдельно сохранить необходимые глобальные объекты/роли. Установить ограниченные права доступа; безопасно хранить сведения о ролях и паролях.
- [ ] Сделать копии конфигурации приложения, PM2, загрузок и необходимых настроек сервера. Получить контрольные суммы и копию за пределами VPS; проверить возможность скачать её обратно.
- [ ] Проверить дамп и роли перед восстановлением. Дамп потенциально затронутой БД может содержать исполняемые объекты; не восстанавливать его без проверки от имени суперпользователя на доверенном рабочем сервере. Для разбора использовать изолированную среду с ограниченным сетевым доступом и без production-секретов.
- [ ] Выполнить полное пробное восстановление в отдельную БД/кластер. Пересоздать только необходимые роли, права и расширения; не переносить неизвестные привилегии вслепую. Проверить владельцев, последовательности и ограничения, выполнить `ANALYZE`.
- [ ] Сравнить контрольные выборки и количества, выполнить чтение и запись тестовых данных. Зафиксировать время восстановления и запас места. Не запускать из репетиции реальные письма, платежи или обработчики заказов.

Условие перехода: успешное восстановление, совпавшие контрольные данные, пригодный внешний бэкап и измеренное окно простоя. Не копировать каталог данных из живого Docker-тома в каталог системного PostgreSQL.

## Этап 3. Подготовка системных служб

1. Установить PostgreSQL **16**, не совмещая смену платформы с обновлением major-версии. Выбрать поддерживаемый patch-релиз и совместимые расширения. До установки учесть автоматическое создание/запуск кластера пакетами Ubuntu: не допустить захвата production-порта.
2. Подготовить новый кластер на временном `127.0.0.1:5433`. Реальное имя instance-unit определить по созданному кластеру (часто `postgresql@16-main`); статус агрегатного `postgresql.service` сам по себе недостаточен.
3. Настроить loopback, `pg_hba.conf`, SCRAM-аутентификацию и отдельную роль приложения с необходимыми правами без административных возможностей. Проверить права, требуемые скриптами миграций Medusa. Пароль менять внутри БД и в приложении согласованно.
4. Установить Redis из доверенного источника на временном `127.0.0.1:6380`, до первого запуска настроив ACL/авторизацию, protected mode, каталоги и права. Не выбирать автоматически старую пакетную версию и не считать текущую 7.4.8 заведомо безопасной: проверка поддерживаемой версии и исправлений обязательна.
5. Предпочтительный вариант для Redis — **новое пустое хранилище сессий**. Пользователям потребуется повторный вход. Не переносить прежние ACL, RDB, репликацию или модули после обнаруженной подозрительной активности. Если инвентаризация выявит бизнес-данные/очереди, сначала подготовить отдельный проверенный способ переноса; не терять их молча.
6. Использовать штатные systemd units и drop-in-настройки при необходимости. Настроить автозапуск, восстановление после сбоя с ограничением частоты, права системных пользователей, лимиты ресурсов, ротацию журналов. PostgreSQL и Redis не должны работать от root.
7. Проверить политику сохранения сессий Redis и допустимую потерю сессий после рестарта; настроить persistence под выбранную политику. Проверить предупреждение `vm.overcommit_memory` из лога и применить подходящую настройку после оценки памяти VPS.
8. Проверить положительное подключение приложения с авторизацией и отказ подключения без неё. Наличие только loopback-публикации дополнить внешней проверкой портов IPv4/IPv6 и правилами firewall.

## Этап 4. Переключение production

Последовательность выполнять только после репетиции и проверки доверия к данным/хосту:

1. Включить страницу обслуживания с HTTP 503 и `Retry-After`. Остановить приём заказов, админские изменения, импорты, расписания и другие источники записи; затем остановить backend/worker-процессы. Проверить отсутствие продолжающихся записей и долгих транзакций.
2. Снять **финальный** дамп старой БД после остановки записей, проверить его, сохранить контрольные данные и внешнюю копию. Репетиционный дамп для переключения не использовать.
3. Восстановить финальный дамп в чистую подготовленную системную БД на 5433, проверить контрольные данные и права. Не накладывать его поверх репетиционных данных без очистки именно тестового целевого кластера.
4. Остановить старые контейнеры, отключить их автоподъём на период наблюдения. Сохранить контейнеры, тома и образы для контролируемого отката. Убедиться, что порты 5432/6379 освобождены.
5. Перевести системный PostgreSQL с 5433 на `127.0.0.1:5432`, Redis с 6380 на `127.0.0.1:6379`, перезапустить соответствующие службы. На одном порту должен быть только один сервер.
6. Обновить серверные секреты и адреса в исходном checkout, активном релизе и фактическом окружении PM2. Проверить generated ecosystem-файлы: сохранённые PM2 env имеют приоритет и могут вернуть старые реквизиты. В URL использовать корректное кодирование значений; секреты не печатать.
7. Запустить backend с обновлённой конфигурацией. Проверить SQL-запрос под ролью приложения и Redis с авторизацией, затем вход и операции приложения. Не выполнять обычный полный deploy только ради изменения адресов: он запускает дополнительные скрипты изменения данных.
8. Провести проверки ниже, снять обслуживание и разрешить записи только после их успешного завершения. Зафиксировать время первой записи в новой БД — с этого момента простой возврат к старому тому недопустим.

## Этап 5. Приёмка

- [ ] PostgreSQL: проверка соединения и чтение/запись под ролью приложения; совпадение данных, расширений, владельцев и последовательностей.
- [ ] Redis: авторизованный PING, сохранение и чтение сессии; неавторизованный клиент получает отказ. Внешние 5432/6379 недоступны по IPv4 и IPv6.
- [ ] Вход в админку, обновление страницы с сохранением сессии, выход и повторный вход; вход покупателя, если используется.
- [ ] Товары, цены, остатки, корзина и оформление тестового заказа; платежи проверять в безопасном тестовом режиме, не списывая реальные деньги.
- [ ] Контролируемая проверка импорта и переводов без массового повторного импорта каталога. Нет повторной отправки событий или писем.
- [ ] Загрузки изображений доступны из прежних путей; существующие медиа не потеряны.
- [ ] `/health`, sitemap, robots.txt, текущие карточки SR/EN, canonical/hreflang работают. Старые удалённые товарные URL остаются HTTP 404 без переадресаций; не возвращать снятые ранее redirects. Количество страниц сверять с текущим каталогом, не с историческим числом 42.
- [ ] В свежих журналах нет ошибок PostgreSQL/ioredis. Проверены задержки, память, диск и стабильность на обычной нагрузке.
- [ ] Проверена перезагрузка VPS в согласованное окно: поднимаются PostgreSQL, Redis, PM2 и приложения; Docker для этого не нужен.

## Этап 6. Откат

| Момент сбоя | Действия |
| --- | --- |
| До переключения | Остановить подготовленные системные экземпляры; продолжить работу с прежней БД и защищённым Redis. Исправить план |
| После переключения, до разрешения записей | Остановить приложения и новые службы, освободить порты, вернуть прежний PostgreSQL с сохранённым томом и согласованными актуальными реквизитами. Проверить приложение до снятия обслуживания |
| После появления записей в новой БД | Снова закрыть запись. Сохранить новый финальный дамп и перенести актуальные данные в отдельно подготовленный совместимый экземпляр для отката либо исправить новый сервис. Прямое включение старой копии потеряет новые заказы |

При любом откате сохранить диагностику. Не запускать два production-писателя параллельно. Не восстанавливать публичные порты, слабые пароли или подозрительное состояние Redis. Redis можно вернуть как чистый изолированный экземпляр с авторизацией и повторным входом пользователей. Отдельно проверить поведение старого релиза с обновлёнными секретами, если откат затрагивает приложение.

## Этап 7. Закрепление в Git, CI и удаление Docker

Выполнять поэтапно: документация и подготовка → перенос → наблюдение → удаление. Предлагаемый период наблюдения: не менее 7 суток, включая перезагрузку, успешный обычный deploy и восстановление внешнего бэкапа; это плановый критерий, не уже пройденная проверка.

| Файл / область | План изменения |
| --- | --- |
| `DEPLOY.md`, `README.md`, `docs/ENVIRONMENT.md`, `docs/README.md` | Установка через APT, systemd, секреты, диагностика, backup/restore, запуск без Docker |
| `scripts/deploy-vps.sh` | Проверка нативных зависимостей и совместимого `pg_dump`; сохранить блокировку, бэкапы, релизы и media. Проверить, что env предыдущего PM2 не переопределяет новые секреты |
| `scripts/activate-release.sh` и откат релизов | Проверить доступ к системным службам и отсутствие восстановления устаревших env при rollback |
| `.github/workflows/deploy.yml` | Учесть, что любой push в main сейчас запускает production-deploy; публикацию документации и реализацию миграции планировать отдельно |
| `.github/workflows/verify.yml` | Заменить PostgreSQL service container на установку/запуск PostgreSQL 16 непосредственно на runner; явно задавать версию, порт, тестовую БД и проверки готовности; сохранить тесты Node 20/24 |
| Локальная разработка | Описать запуск нативных PostgreSQL/Redis, для Windows — в WSL; убрать обязательность Compose |
| `docker-compose.yml` и остальные Docker-ссылки | Удалить из активной конфигурации после завершения отката; исторические отчёты могут сохранять сведения о Docker |

- [ ] Добавить штатные сценарии резервного копирования с systemd timer, защищённым хранением реквизитов и внешней копией. Начальная цель: ежедневные копии и перед изменениями; при приёме реальных заказов определить допустимую потерю данных и при необходимости добавить WAL/PITR. Ежедневный dump не даёт RPO=0.
- [ ] Настроить мониторинг доступности, ошибок резервирования, свободного места, памяти, сроков хранения и ростов журналов; проверить доставку уведомлений выбранному владельцу.
- [ ] После периода наблюдения сохранить последний проверенный внешний backup и необходимую диагностику. Только затем удалять старые контейнеры/тома целевыми операциями, по проверенным именам. Не использовать массовые `prune` или `down -v` как процедуру миграции.
- [ ] Проверить отсутствие других зависимостей, остановить/отключить Docker и его socket; повторить smoke-проверку приложений.
- [ ] Удалить только установленные Docker-пакеты и ненужный runtime после инвентаризации. Не удалять containerd, если его использует другой сервис. Сохранить независимые правила firewall.
- [ ] Возобновить автоматические деплои; убедиться, что новый deploy и reboot не возвращают контейнеры и старые реквизиты.

## Критерии завершения

1. Production PostgreSQL и Redis работают как защищённые системные службы; приложение и SEO-проверки проходят.
2. Нет потери подтверждённых записей; проверено восстановление внешней резервной копии.
3. Пройден период наблюдения и проверка перезагрузки; документированы фактические версии, пути и команды эксплуатации.
4. Проект и CI не требуют Docker; Docker удалён с VPS после проверки сторонних зависимостей.
5. Последствия инцидента разобраны отдельно; отказ от Docker не используется как доказательство устранения компрометации.
