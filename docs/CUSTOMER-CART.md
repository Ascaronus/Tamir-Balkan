# Корзина аккаунта

После успешного входа витрина вызывает `POST /store/customer-cart` с регионом, страной
и необязательным ID гостевой корзины. Владелец берётся только из проверенной сервером
сессии покупателя; Customer ID от браузера не принимается.

Сервер возвращает последнюю незавершённую корзину аккаунта для региона и канала продаж.
Сохраняются исходные строки и количества, даже если доступный остаток стал меньше или 0.
При выходе видимая корзина сбрасывается, но серверные данные сохраняются. Повторный вход,
включая другое устройство, восстанавливает ту же корзину. Запоздавшие ответы старой сессии
не меняют состояние нового пользователя. Завершённые заказы не восстанавливаются как корзины.

## Привязка и гостевая покупка

`tamir_customer_cart` хранит `cart_id` (PK/FK cart), `customer_id` (FK customer), `created_at`;
есть индекс владельца и каскадное удаление при физическом удалении исходных записей.
Эта отдельная серверная запись подтверждает авторизованную привязку: штатная Medusa может
установить customer_id гостевой корзины только по совпадению email, что не доказывает владение.
Произвольная metadata корзины не влияет на привязку.

Если сохранённой корзины аккаунта нет, его текущая гостевая корзина в том же регионе/канале
переносится через штатный workflow Medusa. Чужая привязанная корзина не переносится.
Конкурентные восстановления и привязки сериализуются транзакционными advisory locks PostgreSQL.
Если корзина аккаунта уже есть, она имеет приоритет: отдельная гостевая корзина остаётся
в браузере для гостевого режима и автоматически не объединяется с корзиной аккаунта.

localStorage содержит только гостевой указатель. ID восстановленной корзины аккаунта туда
не записывается. Успешно привязанный гостевой указатель очищается; неудачный запрос не создаёт
пустую замену и не уничтожает указатель. Оформление аккаунта также не очищает отдельную
гостевую корзину.

Для привязанных корзин middleware на `/store/carts/*` проверяет владельца перед чтением,
мутациями, завершением и штатным переносом на покупателя: без авторизации 401, чужому аккаунту
404. Обычное гостевое оформление остаётся доступным. Восстановление требует publishable key
с одним каналом продаж, как в текущей конфигурации магазина. Новых секретов нет.

## Установка

Используется существующий идемпотентный `backend/src/scripts/setup-reviews.ts`, который
уже запускается штатным staging/production deploy перед активацией релиза. При ручной установке
после стандартных миграций Medusa выполнить из backend:

```sh
npx medusa exec ./src/scripts/setup-reviews.ts
```

Сначала нужно создать таблицу, затем запускать новый backend. Изменение аддитивное;
существующие корзины и заказы не переписываются. Не удалять таблицу при откате кода.

Ранее потерянные анонимные корзины, для которых уже удалён браузерный ID, нельзя безопасно
восстановить по email. Старая корзина с сохранившимся ID может быть привязана при входе
после обновления. Подбор старых корзин по email намеренно не выполняется.

## Проверка

- Frontend: `npm test` — восстановление, смена аккаунта, поздние ответы, очистка гостевого
  указателя только после привязки, ошибки сети, предупреждения SR/EN для 0 и недостаточного остатка.
- Backend: `npm run test:cjs -- --no-db` — авторизация, валидация, выбор корзины, привязка,
  отказ чужому пользователю, ошибки хранилища.
- HTTP/PostgreSQL: `npm run test:integration:http -- --testPathPattern=customer-cart` —
  конкуренция, штатные workflows, сохранение строк, запрет чужого/анонимного доступа,
  гостевое оформление с email существующего аккаунта и новая корзина после завершения.
  Запускать только на изолированной тестовой БД по TESTING-RULES.md.
- На stage: добавить несколько товаров, выйти, войти повторно; изменить остаток/резервы
  в отдельной сессии, открыть корзину, проверить 0 и уменьшившийся остаток, уменьшение/удаление,
  затем повторить с другим аккаунтом и с гостевой покупкой.
