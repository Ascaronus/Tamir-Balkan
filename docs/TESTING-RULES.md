# Правила тестирования (для инженеров и AI-агентов)

Свод обязательных правил для всех, кто пишет или меняет тесты в этом репозитории — в том числе AI-агентов
(Codex и аналогов), которые получают задачу вместе с этим документом. Документ самодостаточен: знание репозитория
не требуется. Полные детали и каталог тестов — [TESTING.md](TESTING.md); контракты поведения — `openspec/specs/`
и `openspec/changes/*/specs/`.

## 1. Жёсткие запреты

1. **Не удалять и не «объединять» существующие тесты.** Если тест слабый или его имя не соответствует слою —
   сохранить его, задокументировать границу и закрыть пробел тестом более высокого слоя.
2. **Не менять поведение приложения под предлогом теста.** Тест подстраивается под корректное поведение,
   а не наоборот; правка продакшн-кода допустима только если задача явно про баг.
3. **Никогда не запускать тесты против боевой БД.** Строка подключения с именем базы без `_test`/`_tests`
   (см. §4) должна быть отвергнута до первого запроса, а не «надейся и беги».
4. **Не дублировать внешний E2E.** Браузерные journey, Mailpit-доставка писем и black-box проверки живут
   в отдельном репозитории Tamir-QA-Automation; здесь их не воспроизводить.
5. **Не править CI-манифест, чтобы «подключить» новый тест.** Discovery сам находит файлы в масках (§2);
   правка `.github/workflows/verify.yml` нужна только для принципиально нового шага.
6. **Не трогать `docs/02_EXISTING_TESTS_AUDIT.md`** — это зафиксированный аудит, не рабочий документ.
7. **Не оставлять артефакты прогонов в Git** (`backend/reports/`, `*.xml`, `*.tap`, `*.json` прогонов).

## 2. Где создавать тест: зоны и маски

Тест попадает в CI только если лежит в одной из масок. Новый файл вне масок CI не увидит.

| Зона (путь и маска) | Как запускается | Что это |
|---|---|---|
| `backend/tests/*.test.cjs` | `npm run test:cjs` (discovery `test-support/run-tests.mjs`) | unit/handler-тесты Node |
| `backend/tests/*.integration.cjs` | тот же discovery, категория «нужна БД» | реальный SQL против отдельной PostgreSQL |
| `backend/tests/rozetka-native.ts` | отдельный CI-шаг `npx medusa exec` | сценарий import-workflow на базе `*_import_test` |
| `backend/integration-tests/http/*.spec.[jt]s` | `npm run test:integration:http` (Jest, `medusaIntegrationTestRunner`) | реальный in-app HTTP |
| `frontend/tests/*.test.mjs` | `npm test` (`node --test` + TS-loader `test-support/register.mjs`) | unit/handler/component фронта |
| `frontend/test-support/verify-localized-routes.mjs` | `node test-support/verify-localized-routes.mjs` | собранный Next на `127.0.0.1:3137` + статическая сверка маршрутов |

Медусовские зоны `src/**/__tests__` (jest `TEST_TYPE=unit|module`) в CI не запускаются и сейчас пусты —
не создавать тесты там без явного согласования.

Discovery backend-тестов классифицирует файл как «нужна БД», если имя оканчивается на `.integration.cjs`
**или** в исходнике встречается маркер `/_DB_URL|postgres(ql)?:\/\//. Поэтому:

- тесту с БД либо имя `*.integration.cjs`, либо чтение `*_DB_URL`/`postgres://` в коде — иначе он уедет
  в категорию «без БД» и упадёт;
- после добавления файла самопроверка: `npm run test:cjs -- --list` — файл в списке, категория верная.

## 3. Слои: выбирать по границам, а не по имени

Слой нового теста: `unit` (чистые функции) → `handler` (обработчик с фейковыми `req/res`) →
`component` (UI на harness) → `db-integration` (реальная PostgreSQL) → `http-integration` (реальный in-app
HTTP) → `scenario` (скрипт на одноразовой базе). Правило усиления: пробел, закрытый слабым тестом,
закрывать тестом **самого высокого практически достижимого слоя**, сохраняя старый.

Имя теста обязано соответствовать слою: `http` в имени — только если тест реально поднимает HTTP
(`integration-tests/http/*.spec.ts` или `verify-localized-routes`); фейковые `req/res` — это `handler`.

## 4. База данных и окружение

- Имя любой тестовой базы обязано заканчиваться на `_test`/`_tests`: контракт гарда
  `test-support/guard-env.cjs` (`/(^|[_-])tests?$/i`). Гард вызывается автоматически: discovery-helper
  перед БД-категорией (отказ `exit 2`), Jest-setup (`integration-tests/setup.js`) и CI-шаг
  `node test-support/guard-env.cjs --require-env` (нарушение — код возврата 1).
- SQL-интеграции (`*.integration.cjs`) читают **`TEST_REVIEWS_DB_URL`** — отдельную базу
  (в CI это `review_test`). Не изобретать свою переменную и не подставлять `DATABASE_URL`.
- Jest HTTP-суита (`test:integration:http`) требует PostgreSQL-сервер через `DB_HOST`/`DB_USERNAME`/
  `DB_PASSWORD`/`DB_PORT` и Redis (`REDIS_URL`); runner сам создаёт временные базы `medusa-*-integration-*`.
  `DB_HOST` обязан быть `localhost`: `@medusajs/test-utils` включает SSL для любого другого хоста.
- `tests/rozetka-native.ts` — только база с суффиксом `_import_test`, порядок: создать базу →
  `npx medusa db:migrate` → `npx medusa exec ./src/scripts/setup-reviews.ts` (схемы `tamir_product_url`
  и отзывов создаёт этот скрипт, не миграции) → `npx medusa exec ./tests/rozetka-native.ts`.
- Не запускать параллельно два прогона на одной тестовой базе (в частности Jest-суиту и `--db-only`
  на `review_test`) — данные и схемы мешаются.

## 5. Локализация en/sr

Тесты покрывают **английский и сербский** языки витрины (не русский):

- маршруты парами: `/en/...` ↔ корневой (сербский) вариант; статусы, редиректы и `<html lang>` — в
  `verify-localized-routes.mjs`;
- в фикстурах и утверждениях — реальные Unicode-строки; сербский латиницей с диакритикой
  (нужно различать `en`/`sr` версии проверяемых ключей); кириллица — только если проверяется именно она;
- для переводов UI читать настоящие `frontend/src/messages/en.json` и `sr.json`, а не абстрактные
  маркеры вида `t_title` — правка любого из двух файлов обязана ронять такой тест (tripwire).

## 6. Качество теста

- Один тест = одно поведение; утверждения конкретные (код ответа, поля, сообщения об ошибках,
  негативные сценарии). Пустой smoke «не упало» не закрывает требование.
- Внешние сервисы (SMTP, Google Translate, Turnstile, платёжки) мокируются на границе, и граница
  видна из кода/имени теста; мок не должен доказывать то, что делает только живой сервис.
- Тесты backend не должны зависеть от порядка запуска; для проверки — `npm run test:cjs -- --reverse`.
- Случайное падение (flaky) лечить стабильностью теста, а не удалением/скипом. Зависание шага
  `test:integration:http` в CI уже случалось — это признак проблемы окружения прогона (перезапуск),
  а не повод править тесты.
- Гейта покрытия в CI нет; покрытие не целевая метрика, но новый код задачи обязан иметь тест,
  воспроизводящий требование из задачи.

## 7. Самопроверка перед сдачей задачи

Все команды — из соответствующего каталога, обе Node-матрицы CI (20.20.2 и 24):

```bash
cd backend
node test-support/guard-env.cjs --require-env              # окружение безопасно (только тестовые базы)
npm run test:cjs -- --list                                 # новые файлы в списке, категории верные
npm run test:cjs -- --no-db --junit-dir=reports
# TEST_REVIEWS_DB_URL указывает на базу *_test:
npm run test:cjs -- --db-only --junit-dir=reports
npm run test:integration:http                              # если затронута HTTP-зона
cd ../frontend
npm test
npm run lint -- --quiet
node test-support/verify-localized-routes.mjs              # если затронуты маршруты/локализация
```

CI (`verify.yml`) делает это сам на push в `main` и на PR: гард → `--no-db` → `rozetka-native`
на `_import_test` → `--db-only` → Jest HTTP → загрузка артефактов `backend/reports/`.
Локальные прогоны должны совпадать по составу (за минусом артефактов).

## 8. Definition of Done для тестовой задачи

- [ ] Новые тесты лежат в масках §2 и видны в `--list` / `npm test` / Jest-маске.
- [ ] Ни один существующий тест не удалён, не заскипан и не ослаблен.
- [ ] Все прогоны §7 зелёные на обеих Node; JUnit/Jest-отчёты создаются (для backend).
- [ ] Боевые строки подключения не использованы; обход гарда не допускается.
- [ ] Локализация en/sr проверена, если задача касается витрины, маршрутов или текстов.
- [ ] Документация обновлена: новые тестовые зоны/команды — в `docs/TESTING.md`; команды —
      в `package.json`; поведение — в OpenSpec-спеках при изменении контрактов.
- [ ] PR проходит CI; merge — только с явного разрешения владельца репозитория.
