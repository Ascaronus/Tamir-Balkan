# Секреты TAMIR: хранение вне Git

Правило проекта: действующие пароли, приватные ключи и полные строки подключения не хранятся в файлах GitHub-репозитория, его issues, PR или логах CI. Код читает их из окружения. В Git находятся только пустые `.env.example`, имена переменных и инструкции.

Это правило хранения, а не утверждение, что история Git уже очищена или пароли на VPS уже заменены. Ранее в конфигурации присутствовали общий пароль PostgreSQL и запасные значения JWT/COOKIE. Если они применялись на сервере, считайте их раскрытыми и замените. Удаление из новой версии не удаляет старые коммиты и чужие копии.

## Где находятся значения

| Что | Рабочее место хранения | Что разрешено в Git |
| --- | --- | --- |
| Пароль PostgreSQL для Compose | `/root/tamir_balkan/.env`, переменная `POSTGRES_PASSWORD` | `.env.example` с пустым значением |
| Подключение к БД, Redis, JWT, COOKIE, SMTP, CAPTCHA, перевод | `/root/tamir_balkan/backend/.env`, окружение активного релиза/PM2 | `backend/.env.example` без секретов |
| Адреса витрины, publishable key Medusa, site key Turnstile | локальные env-файлы frontend | Пустой `frontend/.env.example` |
| Ключ SSH для деплоя | GitHub Actions Secrets, отдельно от Git-файлов | Только имя `VPS_SSH_KEY` |
| Ключи владельца для SSH | защищённое хранилище владельца | Только инструкция настройки |
| Копии env, PM2 и базы | закрытые резервные копии VPS и зашифрованная копия владельца | Никаких значений или дампов |

GitHub Actions Secrets — отдельное защищённое хранилище GitHub, поэтому фраза «секретов вообще нет на GitHub» была бы неточной. Приватный ключ автоматического деплоя остаётся там, пока используется этот способ деплоя. Секреты приложения не требуется передавать в Actions: сборка на VPS использует локальное окружение.

`NEXT_PUBLIC_*` попадает в браузер. Здесь допустимы публичные адреса, publishable key Medusa и Turnstile site key. Пароли БД, JWT, SMTP, секретный ключ Turnstile и административные API-ключи туда не помещаются.

## Новая локальная установка

1. Скопируйте `.env.example` в `.env`, `backend/.env.example` в `backend/.env`, `frontend/.env.example` в `frontend/.env.local`. Не перезаписывайте существующие файлы.
2. Сгенерируйте в менеджере паролей отдельные случайные значения для БД, JWT и COOKIE. Для JWT/COOKIE нужно минимум 32 символа; удобный вариант — 32 случайных байта в hex, то есть 64 символа. Пароли не должны совпадать между dev и production.
3. В корневом `.env` задайте пароль БД. В `backend/.env` заполните `DATABASE_URL` в формате `postgres://medusa:<пароль>@127.0.0.1:5432/medusa-v2`. Пароль внутри URL должен быть URL-encoded; для hex это не требуется. Заполните JWT/COOKIE и остальные нужные переменные.
4. На Linux ограничьте права реальных env-файлов до `600`. Запустите `docker compose config --quiet`, затем обычные команды из README. Не публикуйте вывод `docker compose config` без `--quiet`: он содержит подставленные значения.

Compose прекращает выполнение, если `POSTGRES_PASSWORD` не задан или пуст. Backend прекращает запуск/сборку, если JWT/COOKIE отсутствуют, слишком короткие или содержат очевидные шаблоны. Это проверка наличия конфигурации, а не доказательство случайности или безопасности произвольного пароля.

## Существующий VPS: порядок до объединения PR

Push в `main` автоматически запускает деплой. Сначала подготовьте сервер, затем объединяйте изменение.

1. Сохраните текущую рабочую конфигурацию и резервную копию БД в закрытом месте. Не удаляйте Docker volumes. Проверка списка архива `pg_restore --list` не заменяет пробное восстановление в отдельную БД.
2. Создайте корневой `.env` с текущим паролем PostgreSQL, пока не проведена его согласованная замена. Для существующего volume переменная `POSTGRES_PASSWORD` не выполняет `ALTER ROLE` и сама по себе не меняет пароль.
3. Проверьте источник окружения backend: исходный `backend/.env`, env активного релиза, `.medusa/server/.env.production` и значения PM2. Скрипт старта создаёт `.env.production` только при отсутствии файла. Старое значение PM2 может перекрыть новое значение в файле; `pm2 restart` сам по себе не синхронизирует все эти источники.
4. Замените ранее раскрытые значения согласованно. Смена пароля БД требует изменения роли PostgreSQL и всех её клиентов, включая `DATABASE_URL`, корневой `.env` и резервное копирование. Делайте это в согласованное окно обслуживания. Не вставляйте пароль в командную строку, Git-коммит или переписку.
5. Сгенерируйте отдельные JWT/COOKIE, обновите рабочие источники окружения и проверьте их до активации релиза. Смена этих ключей может потребовать повторного входа пользователей. Если провайдерский ключ был опубликован, отзовите его у провайдера и замените локально.
6. Сохраните локальные исправления Compose на VPS: привязку обоих портов к `127.0.0.1` и политику перезапуска Redis. Согласуйте их с PR, потому что deploy-скрипт останавливается при изменённых отслеживаемых файлах. Не используйте `git reset --hard` для удаления серверных правок.
7. Проверьте конфигурацию без вывода значений, выполните обычный деплой и проверьте вход администратора, запросы магазина и отправку письма. Только после этого считайте перенос конфигурации завершённым.

Этот PR не меняет пароли на VPS, не включает Redis ACL/пароль автоматически и не переписывает историю Git. Привязки портов к loopback сохраняются. Переход от Docker к системным сервисам не меняет правила хранения секретов.

## Как сохранить действующие файлы на своём компьютере

Скачиваемый комплект шаблонов не содержит текущих паролей VPS. Скопируйте реальные env-файлы с сервера напрямую через SFTP/WinSCP в отдельную папку вне клона проекта. Не пересылайте их в чат.

Минимально сохраните исходные файлы: корневой `.env` (если уже создан), `backend/.env` и реально используемые env-файлы frontend. Сохраните также конфигурацию активного релиза и значения, которые существуют только в PM2: одного исходного `.env` может быть недостаточно для восстановления. Путь активного релиза можно посмотреть через `pm2 describe tamir-backend` и `pm2 describe tamir-frontend`; не публикуйте вывод с чувствительными данными.

Пример копирования одного файла в PowerShell **на вашем компьютере**; замените `VPS_HOST` адресом VPS. SSH запросит доступ обычным способом:

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\tamir-private"
scp root@VPS_HOST:/root/tamir_balkan/backend/.env "$env:USERPROFILE\tamir-private\backend.env"
```

Импортируйте полученные файлы в менеджер паролей с вложениями или зашифрованный архив и ограничьте доступ к папке. Обычный ZIP без шифрования не защищает пароли. Не сохраняйте эту папку в Git; имя `backend.env` само по себе не гарантирует игнорирование Git. После ротации обновите резервную копию. Старые копии могут содержать уже отозванные секреты и данные клиентов.

## Контроль перед коммитом

`.gitignore` исключает настоящие `.env`, распространённые ключи, дампы, `.secrets/`, `secrets-local/` и сгенерированный `ecosystem.config.cjs`. Он не удаляет уже отслеживаемые файлы, не блокирует `git add -f` и не находит секреты в произвольном исходном коде.

Перед коммитом проверяйте `git diff --cached` локально и список добавляемых файлов. Не публикуйте полный diff, если нашли в нём секрет. Тестовые credentials одноразовой базы CI — фикстуры, не учётные данные production; настоящие ключи CI не нужны. JWT/COOKIE для проверки сборки генерируются заново в каждом CI job.

Очистка истории — отдельная операция после отзыва раскрытых значений. Она затрагивает коммиты, ветки и клоны, поэтому не выполняется этим изменением автоматически.

## Что проверено при подготовке

В доступных Git-объектах проверены 125 коммитов и текстовые файлы на типовые ключи, строки подключения и секреты конфигурации. Обнаружены встроенный пароль БД, запасные JWT/COOKIE и примеры; подтверждённых приватных ключей или ключей провайдеров по использованным шаблонам не найдено. Это ограниченный поиск, не гарантия отсутствия утечек: он не охватывает содержимое VPS, Actions Secrets, все логи/артефакты, чужие клоны и недоступные/удалённые объекты.
