# Карусель баннеров

Макет подготовлен перед реализацией: https://www.figma.com/design/2u9V1x7faa2yieZqRP0KaF?node-id=223-3703

## Управление

Medusa Admin → Extensions → Homepage Banners. Независимые тексты SR/EN, desktop/mobile изображения, два CTA, положение и тон текста, градиент и fit изображения. Порядок меняется перетаскиванием или кнопками вверх/вниз. UI не ограничивает число строк; технический серверный предел — 1000 баннеров в документе.

Save Draft сохраняет рабочую карусель без изменения витрины. Publish у строки публикует только эту версию баннера. Publish settings & order применяет настройки и порядок уже опубликованных баннеров. Publish carousel атомарно публикует всю подготовленную карусель. Публикация, деактивация, удаление и восстановление требуют подтверждения. Перед публикацией несохранённая форма сохраняется как черновик. Ошибка публикации сохраняет старую публичную версию и новый черновик; UI получает актуальную revision после сохранения.

Preview и Preview Carousel показывают рабочий объект, включая несохранённые изменения. Desktop 1200px, Tablet 768px, Mobile 390px, SR/EN. Ссылки не выполняют переход. Одиночный предпросмотр неактивного баннера временно показывает его без изменения данных.

## Хранение и установка

`setup-reviews.ts`, уже запускаемый штатным deploy-vps.sh, создаёт `tamir_homepage_carousel` и `tamir_banner_media`. Первый документ сохраняет существующий `/design/tamir-family-winter.webp`, оба текущих перевода и CTA. Повторный setup не перезаписывает контент. При ручной установке выполнить этот setup после стандартных миграций.

В JSONB хранятся draft, published и одна предыдущая опубликованная карусель. Изменения — в транзакции с блокировкой строки и проверкой revision; устаревший конкурентный запрос получает 409. Restore восстанавливает предыдущую публикацию целиком, сохраняя существующие черновики; отсутствующие в черновике восстановленные баннеры добавляются обратно в список для редактирования. Это не бесконечная история версий.

Загрузки находятся в `static/banners` и входят в существующее сохранение runtime media между релизами. Нельзя удалять прежний каталог, на который указывает media symlink. Имена генерируются сервером, имя файла от клиента не используется как путь. Удаление баннера/замена изображения не удаляет физический файл: его могут использовать другой баннер и предыдущая публикация. Автоматическая очистка файлов не добавлена. Этот каталог следует включать в резервные копии.

PNG/JPEG/WebP/AVIF проверяются по base64, сигнатуре, MIME и размеру. SVG запрещён. Лимит 5 MiB, серверная настройка `BANNER_MAX_UPLOAD_BYTES` до технического предела 20 MiB согласована с JSON body limit. Публикация принимает только зарегистрированные файлы, существующие на диске, либо исходный versioned hero. Сервер не скачивает произвольные URL. `MEDUSA_PUBLIC_BACKEND_URL` — публичный HTTPS URL, fallback https://api.tamir.rs.

Административные операции проверяют Medusa-сессию и актуального пользователя. По существующей схеме модерации разрешён `admin@tamir.local`; дополнительные адреса задаются серверной переменной `BANNER_ADMIN_EMAILS` через запятую. Разрешение адреса не заменяет аутентификацию.

## Витрина

`/store/homepage-banners` отдаёт только активные опубликованные версии, без draft, previous и внутренних имён. ETag зависит от revision, Cache-Control требует перепроверки: новая публикация инвалидирует HTTP-кеш, в том числе между процессами. Next читает данные на сервере с no-store. Пересборка не требуется, запросов при переключении слайда нет. Уже открытая страница получает изменения при новой загрузке/навигации; push-обновлений нет.

Первый слайд есть в SSR, его изображение имеет высокий приоритет. Остальные изображения подключаются при первом показе. Тексты всех слайдов участвуют в общей сетке, сохраняя высоту. Desktop Hero — минимум 468px, mobile — текст над изображением 7:4. Длинный контент увеличивает высоту, а не обрезается.

Autoplay 6000ms по умолчанию, варианты 3/4/5/6/8/10/15 секунд. Fade 500ms; пауза на hover/focus, скрытой вкладке и reduced-motion. Ручной выбор сбрасывает интервал, есть отдельная кнопка паузы. Свайп не перехватывает вертикальную прокрутку. Один активный баннер — без индикаторов; ноль — без Hero. Ошибка API показывает исходный Hero как fallback.

## Renderer и проверки

Канонические `banner-model.ts`, `banner-carousel.tsx`, `banner-carousel.css` — в `backend/src/shared`. Medusa использует React 18, Next — React 19 и отдельный build root. Поэтому frontend использует точные копии в `frontend/src/lib/banners/shared`. После правки выполнить `node scripts/sync-banner-renderer.mjs`. Тест проверяет побайтовое совпадение. Шрифт Manrope для admin preview включён локально с OFL-лицензией; витрина сохраняет свой Manrope.

Изучены PR #35 и TESTING-RULES. Маски discovery не меняются:

- `banner-carousel.test.mjs`: реальные SR/EN строки исходного Hero, CTA, первый слайд, таймеры, паузы, свайп, пустое/одиночное состояние, единый renderer.
- `banner-admin.test.mjs`: несохранённая форма в preview, язык/ширина, Save Draft, подтверждение публикации и revision.
- `homepage-banners.test.cjs`: валидация, URL, загрузки, права, публичная проекция и ETag.
- `homepage-banners.integration.cjs`: PostgreSQL, draft/published, конкуренция, откат при ошибке, деактивация/удаление/восстановление.
- `integration-tests/http/homepage-banners.spec.ts`: реальные административные HTTP-маршруты в изолированном Medusa runner.

SQL/HTTP требуют изолированных PostgreSQL/Redis по TESTING-RULES. Браузерные journey и визуальные проверки DnD, контраста, длинных текстов, большого числа индикаторов и мобильного свайпа относятся к внешнему Tamir-QA-Automation. Unit/component их не заменяют. Production-сервисы в тестах не используются.
