# Spec Delta

## Purpose

Возможность `wishlist` описывает избранное покупателя: добавление и удаление товаров сердцем на карточках каталога и странице товара, счётчик в шапке, локализованную страницу `/wishlist`, поведение гостя через модалку входа и серверное хранение в PostgreSQL с жёсткой изоляцией по сессии. Контракт зафиксирован по уже реализованной и влитой реализации (YouTrack TB-14, commit `d9e958e`) и служебной документации `docs/WISHLIST.md`.

## ADDED Requirements

### Requirement: Сердце избранного на карточках товара и странице товара

Карточка товара в каталоге (сетка, карусели, результаты поиска) и блок заголовка страницы товара SHALL показывать интерактивную кнопку-сердце: клик добавляет или удаляет товар из избранного текущего авторизованного покупателя без перезагрузки страницы. Клик по сердцу SHALL NOT инициировать переход по ссылке карточки. Кнопка SHALL иметь `aria-pressed`, локализованный `aria-label` и состояние ожидания на время запроса.

#### Scenario: Авторизованный покупатель добавляет товар с карточки
- **WHEN** авторизованный покупатель нажимает незаполненное сердце на карточке товара
- **THEN** выполняется `POST /store/wishlist` с `product_id` этого товара, сердце становится заполненным и счётчик в шапке увеличивается без перезагрузки страницы

#### Scenario: Клик по сердцу не открывает страницу товара
- **WHEN** покупатель нажимает сердце на карточке, которая является ссылкой на товар
- **THEN** событие клика останавливает всплытие (`stopPropagation`) и переход по ссылке карточки не происходит

#### Scenario: Сердце на странице товара
- **WHEN** покупатель открывает страницу товара и нажимает сердце рядом с заголовком
- **THEN** товар добавляется/удаляется из избранного тем же механизмом, состояние сердца синхронизировано с остальными карточками и шапкой

### Requirement: Гость входит через модалку, действие повторяется ровно один раз

Если гость (без авторизации) нажимает сердце или открывает страницу `/wishlist`, приложение SHALL открыть существующее модальное окно входа из контура `customer-auth` и НЕ SHALL выполнять запрос к API избранного. После успешного входа намерение гостя SHALL быть применено ровно один раз после загрузки состояния избранного аккаунта; при отмене входа не применённое намерение сохраняться НЕ SHALL.

#### Scenario: Добавление после успешного входа
- **WHEN** гость нажимает сердце, успешно входит через модалку и состояние избранного аккаунта загружено
- **THEN** `POST /store/wishlist` с тем же `product_id` отправляется ровно один раз, сердце становится заполненным

#### Scenario: Отмена входа не оставляет ожидающего действия
- **WHEN** гость открыл модалку входа нажатием сердца и закрыл её без авторизации
- **THEN** состояние избранного не меняется, ожидающего намерения нет, и после последующего входа никакой запрос от отправленного ранее намерения не выполняется

### Requirement: Счётчик избранного в шапке

Для авторизованного покупателя в шапке SHALL отображаться ссылка на страницу `/wishlist` с количеством сохранённых товаров. Счётчик SHALL обновляться после добавления/удаления без перезагрузки страницы и перечитываться при возврате фокуса на вкладку браузера. Для гостя ссылка с счётчиком в шапке отображаться НЕ SHALL.

#### Scenario: Ссылка со счётчиком для авторизованного
- **WHEN** авторизованный покупатель открывает любую страницу магазина
- **THEN** в шапке отображается ссылка на `/wishlist` с числом товаров из ответа `GET /store/wishlist` (без бейджа при пустом списке)

#### Scenario: Счётчик уменьшается после удаления
- **WHEN** покупатель удаляет товар из избранного с любой карточки, страницы товара или страницы `/wishlist`
- **THEN** счётчик в шапке уменьшается сразу, без перезагрузки страницы

#### Scenario: Гость не видит счётчик
- **WHEN** неавторизованный посетитель открывает магазин
- **THEN** ссылка избранного с счётчиком в шапке отсутствует

### Requirement: Локализованная страница избранного /wishlist

Авторизованный покупатель SHALL иметь локализованную страницу `/wishlist` со списком сохранённых товаров в порядке добавления (новые первыми): локализованные название, цена, изображение, ссылка на страницу товара и сердце для удаления. Пустой список SHALL показывать локализованное пустое состояние с призывом в каталог; гостю SHALL предлагаться вход без запроса чужого списка.

#### Scenario: Список избранного с удалением
- **WHEN** покупатель с непустым избранным открывает `/wishlist` и нажимает сердце в списке
- **THEN** товары отображаются локализованно, удалённый товар исчезает из списка, счётчик в шапке уменьшается

#### Scenario: Пустое состояние
- **WHEN** покупатель без сохранённых товаров открывает `/wishlist`
- **THEN** отображается пустое состояние (`wishlist.empty`) со ссылкой в каталог, без сетки товаров

#### Scenario: Гость на странице избранного
- **WHEN** неавторизованный посетитель открывает `/wishlist`
- **THEN** отображается блок входа (модалка `customer-auth`), запрос к списку избранного не выполняется

### Requirement: Недоступные товары остаются в избранном заглушкой

Товар, ставший недоступным (снят с публикации или удалён из текущего sales channel), SHALL сохраняться в избранном и отображаться на странице `/wishlist` локализованной заглушкой (`wishlist.unavailable`) с кнопкой удаления; автоматическое удаление таких записей НЕ выполняется. При повторной публикации товара его карточка SHALL восстановиться в списке. Физическое удаление товара каскадно снимает записи избранного на уровне БД.

#### Scenario: Снятый с публикации товар показан заглушкой
- **WHEN** сохранённый товар перестал быть опубликованным в текущем канале продаж и покупатель открывает `/wishlist`
- **THEN** на его месте локализованная заглушка с кнопкой сердца для удаления, запись не удалена

#### Scenario: Товар снова доступен
- **WHEN** товар опубликован заново и покупатель перезагружает страницу `/wishlist`
- **THEN** карточка товара снова отображается с названием, ценой и изображением

### Requirement: API избранного доступно только владельцу и возвращает контрактные ошибки

Эндпоинты `GET/POST /store/wishlist` и `DELETE /store/wishlist/:productId` SHALL работать только при аутентификации покупателя (`bearer`/`session`): без токена или при недействительном аккаунте — `401 LOGIN_REQUIRED`. Некорректный `product_id` SHALL отклоняться с `400` до обращения к БД. Несуществующий или недоступный в канале продаж товар SHALL давать `404 PRODUCT_NOT_FOUND`. `POST` уже сохранённого товара SHALL быть идемпотентен. Все ответы — с `Cache-Control: private, no-store`.

#### Scenario: Неаутентифицированный запрос
- **WHEN** запрос к любому эндпоинту избранного приходит без токена покупателя или с токеном аккаунта без профиля
- **THEN** ответ `401` с кодом `LOGIN_REQUIRED`, обращений к таблице избранного нет

#### Scenario: Некорректный идентификатор товара
- **WHEN** `POST`/`DELETE` получают `product_id`, не соответствующий формату `prod_` + алфавитно-цифровый суффикс (например `../prod_a` или пустая строка)
- **THEN** ответ `400` (`INVALID_PRODUCT`), запрос к БД не выполняется

#### Scenario: Дублирующее добавление идемпотентно
- **WHEN** покупатель повторно отправляет `POST` для уже сохранённого `product_id`
- **THEN** ответ успешный `{ product_id, saved: true }`, в БД ровно одна запись

### Requirement: Хранение избранного уникально и изолировано по покупателям

Избранное SHALL храниться в таблице PostgreSQL `tamir_customer_favorite` с обязательным ограничением `UNIQUE(customer_id, product_id)` и внешними ключами на `customer(id)` и `product(id)` с `ON DELETE CASCADE`. Владелец SHALL определяться исключительно из аутентификационной сессии (`auth_context.actor_id` с проверкой `has_account`), а не из тела или query-параметров запроса. Доступ к записям другого покупателя НЕ возможен.

#### Scenario: Параллельные дубликаты схлопываются в одну запись
- **WHEN** два параллельных `POST` одного покупателя для одного товара завершаются успешно
- **THEN** ограничение уникальности гарантирует ровно одну запись, состояние избранного не «переключается»

#### Scenario: Чужие записи недоступны
- **WHEN** покупатель A запрашивает или удаляет избранное, пока аутентификация соответствует покупателю B
- **THEN** список и операции применяются только к записям владельца сессии, записи другого покупателя не читаются и не изменяются

#### Scenario: Подмена владельца в теле запроса отклоняется
- **WHEN** тело `POST` содержит дополнительные поля (например `customer_id`)
- **THEN** ответ `400 INVALID_BODY`, записи создаются только для владельца сессии

### Requirement: Избранное не хранится в браузере и сбрасывается при logout

Список избранного SHALL храниться только на сервере; запись идентификаторов избранного в `localStorage`, `sessionStorage` или иные браузерные хранилища НЕ выполняется. При logout клиентское состояние избранного SHALL сбрасываться: счётчик в шапке исчезает, сердца возвращаются в незаполненное состояние.

#### Scenario: Logout очищает состояние
- **WHEN** покупатель совершает logout
- **THEN** ссылка избранного в шапке скрывается, все сердца незаполнены, при следующем входе состояние загружается с сервера

#### Scenario: Нет браузерного хранилища
- **WHEN** покупатель работает с избранным (добавление, удаление, страница `/wishlist`)
- **THEN** приложение не выполняет записи `localStorage`/`sessionStorage` с идентификаторами товаров избранного
