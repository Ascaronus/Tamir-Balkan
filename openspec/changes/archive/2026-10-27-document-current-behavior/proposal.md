# Proposal

## Why

В репозитории сейчас ноль спецификаций OpenSpec: всего поведение магазина tamir.rs зафиксировано только в русскоязычной прозе `docs/*.md` и в утверждениях ~45 файлов автотестов. Любая новая функция или миграция оценивается «на глаз», потому что нет формального поведенческого контракта. Эта задача документирует ТЕКУЩЕЕ реализованное поведение приложения — без изменения кода и без выдуманных функций — чтобы дальше работать от спецификаций, а не от догадок.

## What Changes

- Создаются спецификации OpenSpec, описывающие текущее (реализованное) поведение системы: архитектуру и взаимодействие сервисов, каталог/поиск/сортировку/фильтры, корзину и оформление заказа, регистрацию/аутентификацию/подтверждение email, заказы и личный кабинет, отзывы, локализацию SR/EN, SEO/URL/маршрутизацию, импорт Rozetka XML, администрирование, безопасность и контроль доступа, автотесты и CI/CD.
- Каждое требование подкрепляется доказательством из кода, тестов или `docs/`; неподтверждённые выводы явно помечаются как предположения.
- НЕ изменяется код приложения, НЕ меняются тесты, НЕ настраивается CI — это только документирование.
- Реализация ранее подготовленных планов QA-автоматизации в рамках этой задачи НЕ начинается.

## Capabilities

### New Capabilities

- `platform-architecture`: состав системы (backend Medusa v2 :9000, frontend Next.js, PostgreSQL, Redis), конфигурационные ограничения запуска (секреты, cookie), границы кастомного кода и взаимодействие сервисов.
- `product-catalog`: выдача товаров/категорий в store API, поиск, сортировка (в т.ч. по популярности), фильтры, остаточная доступность, дробные атрибуты, локализованные URL товаров.
- `cart-checkout`: создание/обновление корзины, диалог подтверждения добавления, шаги оформления заказа, гостевой checkout, подтверждение заказа.
- `customer-auth`: двухшаговая регистрация с кодом по email, вход, сброс пароля, повторная регистрация удалённого клиента, rate limit входа, политика секретов аутентификации.
- `customer-orders`: заказы в личном кабинете, детальная страница заказа, права доступа к данным заказа (session/guest token).
- `product-reviews`: публикация отзывов (модерация), голосование «полезно», правила отображения, защита от повторных отзывов.
- `localization`: локаль-префиксы `/rs` и `/en`, определение локали (cookie `store_locale` → `Accept-Language` → `sr`), переключатель языка, сербские/английские слаги служебных маршрутов, тексты витрины SR/EN.
- `seo-routing`: canonical/hreflang, sitemap, robots, `noindex` для приватных страниц, JSON-LD, редиректы legacy-URL (301/308), канонизация URL.
- `rozetka-import`: импорт товаров из XML фида Rozetka (native import), маппинг атрибутов, картинки, цены/остатки, идемпотентность повторного импорта, админский запуск импорта.
- `administration`: кастомные страницы/виджеты админки Medusa (`/app`) — rozetka-импорт, отзывы, дробные значения, автоперевод опций; доступ только для авторизованного админа.
- `security-access-control`: обязательные секреты и отказ старта, cookie-политика, rate limiting, CORS, publishable key, защита админ-маршрутов.
- `testing-ci-cd`: обязательные проверки CI (verify.yml: линт, сборка, `node --test` по явному списку файлов, верификаторы локализации и deploy), среда тестов (отдельные БД), модель деплоя (release pin) — как поведенческий контракт конвейера.

## Impact

- Создаются только файлы планирования: `openspec/changes/document-current-behavior/**` (proposal, дельты спецификаций, design, tasks).
- Код приложения, конфигурация, тесты и CI не затрагиваются.
- После применения (apply) дельты попадут в `openspec/specs/**` как основные спецификации проекта.
- Риски: расхождение формулировок с реальной реализацией снижается требованием «каждое требование — со ссылкой на файл/тест»; всё, что не подтверждено кодом, в спецификации не попадает.
