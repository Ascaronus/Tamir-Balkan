# Design

## Context

Мотивация — в `proposal.md` (Why). Текущее состояние, важное для подхода:

- `openspec/specs/` пуст: базовых спецификаций нет, поэтому все 12 возможностей в дельтах описаны как `## ADDED Requirements` (нет `MODIFIED`/`REMOVED`).
- Единственные формальные артефакты поведения сейчас — ~45 файлов автотестов (`backend/tests/`, `frontend/tests/`), русскоязычные `docs/*.md` и сам код. Поведение нигде не сжато в поведенческий контракт.
- Кастомная бизнес-логика backend живёт в `backend/src/utils/**`, `backend/src/api/**`, `backend/src/subscribers/**`; каталоги `src/modules|workflows|links` — заглушки с README, Medusa-workflows не используются. Это граница при разборе «что вообще может быть задокументировано».
- План QA-автоматизации в `docs/02_EXISTING_TESTS_AUDIT.md` — документ пользователя; он описывает БУДУЩИЕ тесты и в спецификации текущего поведения сознательно не отражён.

## Goals / Non-Goals

**Goals:**

- Спецификации-дельты, описывающие только подтверждённое текущее поведение, с проверяемыми сценариями (WHEN/THEN), пригодными для переноса в `openspec/specs/` при apply.
- Явное разделение: подтверждённое поведение (в спеках) ↔ неподтверждённое/неизвестное (только здесь, в разделе «Открытые вопросы» и ниже).
- Нотация требований, совместимая со строгим валидатором OpenSpec (`### Requirement:` ≤500 символов, `#### Scenario:` с **WHEN**/**THEN**/**AND**).

**Non-Goals:**

- Изменение кода, тестов, CI, конфигурации — ничего не меняется (только файлы планирования).
- Реализация планов из `docs/02_EXISTING_TESTS_AUDIT.md` (новые Playwright/E2E-тесты, contract-тесты и пр.) — вне рамок этой задачи.
- Документирование планов roadmap и несуществующих функций; документирование внешнего прод-контура (nginx, DNS, TLS), которого нет в репозитории.

## Decisions

1. **12 возможностей вместо одной большой спеки.** Границы взяты по существующей доменной структуре `docs/` и тестовым файлам (каталог, корзина, auth, заказы, отзывы, локализация, SEO, rozetka, админ, безопасность, архитектура, CI). Альтернатива «одна спека системы» отклонена: нарушило бы правило one-capability-per-folder и сделало бы дельты нечитаемыми.
2. **Критерий включения факта: код + тесты + `docs/`.** Требование попадает в спеку, только если поведение подтверждается исполняемым кодом/тестами (приоритет: тесты → код → docs). Расхождения docs↔код разрешаются в пользу кода (пример: `docs/TESTING.md` отстаёт от `verify.yml` — спека следует за кодом). Альтернатива «документировать по docs/» отклонена: docs местами устарели.
3. **Только `ADDED`-дельты.** Правил MODIFIED нет, т.к. базовых спек нет. При apply дельты станут основными спеками без слияния.
4. **Язык спецификаций — русский, идентификаторы — английские.** Соответствует языку `docs/` и тестовых описаний проекта; модальность «обязана/должна (MUST)» сохраняет семантику RFC 2119 для валидатора.
5. **Спецификации описывают внешнее наблюдаемое поведение, а не внутренности.** Внутренние имена функций не используются в формулировках требований; имена эндпоинтов, env-переменных, таблиц БД (`tamir_review_rate`, `tamir_login_rate`, `tamir_registration_code`, `tamir_password_reset`) и колонок (`code_hash`) сохраняются, потому что это наблюдаемые контракты.
6. **Неподтверждённое вынесено из спек в этот документ** (см. «Неподтверждённые факты»). Альтернатива «включить с пометкой (предположение)» отклонена: валидатор и будущие читатели трактуют спеку как контракт, предположения в ней недопустимы.

## Неподтверждённые факты (не вошли в спецификации)

- Точные HTTP-коды постоянных редиректов legacy-маршрутов: в коде — `permanent: true` (`next.config`) и `redirect()`; числовой код (301/308) тестами не проверяется — в спеке формулировка «постоянный редирект» без числа.
- Конфигурация nginx на VPS (как проксируются `tamir.rs` и `api.tamir.rs`) — вне репозитория; подтверждены только health-URL из `activate-release.sh`.
- Боевые значения секретов (`JWT_SECRET`, Turnstile, SMTP, `VPS_KNOWN_HOSTS`) — в репозитории отсутствуют; задокументированы только правила их проверки (`check-review-config.cjs`, `auth-secrets.test.cjs`).
- Фактическое содержимое внешнего фида `https://tamir.ua/ua/rozetka/` — подтверждён только контракт валидации yml_catalog в коде; ответ источника не проверялся.
- Дрейф документации: `docs/TESTING.md` упоминает интеграционные тесты (product-variants, related-products, full price sync, search), отсутствующие в явном списке `verify.yml`; зафиксирован как риск ниже, спека отражает состояние кода.

## Risks / Trade-offs

- [Спека зафиксировала поведение, которое вот-вот изменится (например, активная ветка QA-автоматизации)] → спецификации описывают срез на коммите `b5558c3`; при изменении поведения дельта/архив обновляется через новый OpenSpec-чейндж, а не редактом основной спеки.
- [Возможный расход формулировки спеки с реальностью из-за объёма кода] → каждое требование выводимо из конкретного файла `backend/tests`/`frontend/tests`/кода; перед apply проведена строгая валидация; неподтверждённое вынесено из спек.
- [Теряется контекст «почему» поведение такое] → спецификации намеренно не объясняют мотивы; мотивы — в `docs/` и коде, спека — контракт.
- [Двойственный статус security-спецификации: middleware-таблица описана и в `platform-architecture`, и в `security-access-control`] → осознанное пересечение (архитектура middleware vs. безопасность лимитов); при необходимости границы уточняются новым чейнджем.
- [`docs/TESTING.md` расходится с CI-контрактом] → спека `testing-ci-cd` следует за `verify.yml`; расхождение docs — кандидат в отдельный чейндж по актуализации документации.

## Migration Plan

1. Apply переносит дельты (`specs/*/spec.md` с `## ADDED Requirements`) в `openspec/specs/<capability>/spec.md` как основные спецификации (слияния нет — базы пустой).
2. Откат не требуется: файлы планирования untracked, код не затронут; удаление `openspec/changes/document-current-behavior/` возвращает состояние до задачи.
3. Деплой/прод не задействованы.

## Открытые вопросы

- Нужно ли в будущем разнести SECURITY-требования middleware между `platform-architecture` и `security-access-control` жёстче — ответ позже, на спеки/задачи не влияет.
- Проверять ли числовые коды редиректов (301/308) отдельными тестами — вопрос будущего QA-чейнджа, не этой задачи.
