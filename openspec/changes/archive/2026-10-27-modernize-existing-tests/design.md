# Дизайн: modernize-existing-tests

## Context

Мотивация — в `proposal.md`. Текущее состояние (проверено ревизией репозитория):

- CI `Verify storefront and backend` (`.github/workflows/verify.yml`): matrix
  Node 20.20.2 / 24, Postgres 16 service, `TEST_REVIEWS_DB_URL`, генерация
  одноразовых `JWT_SECRET`/`COOKIE_SECRET`, npm-кэш. Frontend исполняется
  glob-раннером `node --test tests/*.test.mjs` (28 файлов). Backend-тесты
  запускаются двумя шагами с ручным списком файлов (строки 69 и 71).
- Не запускаются в CI: `backend/tests/registration-email.test.cjs` (мок SMTP),
  Jest-суита `npm run test:integration:http` (единственный тест —
  `backend/integration-tests/http/health.spec.ts`), `backend/tests/rozetka-native.ts`
  (требует отдельную БД `_import_test`).
- `backend/tests/` — 16 `.cjs`-файлов (`*.test.cjs` и `*.integration.cjs`) плюс
  `rozetka-native.ts`. Машиночитаемых отчётов и артефактов CI не создаёт.
- Парность маршрутов `/rs`/`/en` уже проверяет
  `frontend/test-support/verify-localized-routes.mjs` (шаг CI, строка 65).
- Аудит `docs/02_EXISTING_TESTS_AUDIT.md` (v2.0) задаёт фазы P0–P4 и правило
  цепочки «исходный тест → отсутствующая гарантия → тест высшего слоя →
  наблюдаемый результат». Реальные API/E2E-проверения развёрнутых стендов
  принадлежат отдельному репозиторию Tamir-QA-Automation.

## Goals / Non-Goals

**Goals:**
- CI честно обнаруживает и исполняет весь набор тестов; отчёты машиночитаемы.
- Появляются настоящие HTTP-интеграционные проверки in-app границ Medusa.
- Единые правила изоляции (одноразовые БД/секреты, анти-production-барьер).
- Все полезные существующие тесты сохранены и усилены, а не удалены.

**Non-Goals:**
- Изменение рантайм-поведения приложения (bug-fixes, новые фичи) — нет.
- Браузерные E2E, Mailpit-почтовые проверки, black-box тесты стендов — зона
  Tamir-QA-Automation.
- Внедрение Playwright/Cypress или новых фреймворков в этот репозиторий.
- Перевод будущих отчётов QA-дашборда — вне этого change.

## Decisions

### D1. HTTP-интеграция: Jest + `medusaIntegrationTestRunner`, а не самодельный HTTP-сервер

`@medusajs/test-utils` уже в зависимостях (`backend/package.json`), jest 29
настроен (`backend/jest.config.js`, TEST_TYPE-driven), тест существует
(`integration-tests/http/health.spec.ts`). In-app runner сам создаёт/удаляет БД
и даёт `api.get/post`. Альтернатива — поднимать сервер и гонять `fetch` из
`node --test` — дороже и дублирует инфраструктуру Medusa. Выбор: расширять
существующую Jest-суиту новыми spec-файлами (`catalog`, негативы авторизации).

### D2. Discovery backend-тестов: helper-скрипт со glob-поиском, а не glob в `node --test`

Node 20 не поддерживает glob-паттерны в аргументах `node --test` (появились в
Node 22), а matrix CI включает 20.20.2. Решение: `backend/test-support/run-tests.mjs`
— сканирует `backend/tests/` по шаблонам `*.test.cjs` / `*.integration.cjs`,
разделяет «нужна БД» и «не нужна», вызывает `node --test <файлы...>`. Frontend
уже использует рабочий паттерн (`tests/*.test.mjs` в npm-скрипте) — не трогаем.
Альтернатива «поднять minimum Node до 22» отвергнута: сужает матрицу без нужды.

### D3. Машиночитаемые отчёты: встроенный `--test-reporter=junit` c fallback

Для Node 24 reporter junit встроен; для Node 20 — тот же флаг работает
(node:test поддерживает junit-reporter с 20.x), но при проблемах в matrix
допускается единый конвертер TAP→JUnit в `test-support/`. Jest-шаг отдаёт
`jest-jest2xml`-совместимый отчёт через `--reporters` (jest-junit — единственная
новая dev-зависимость, только если встроенных средств не хватит). Артефакты
загружаются `actions/upload-artifact@v4` с `retention-days: 14`.

### D4. Анти-production-барьер: общая функция-гард в `backend/test-support/`

Одна проверка `assertNonProduction(databaseUrl, targetHost)` (стоп-лист боевых
хостов/префиксов `DATABASE_URL`), вызываемая из helper-раннера (D2), Jest-setup
(D1) и `rozetka-native`. Альтернатива «скоуп на уровне прав БД» оставлена как
будущее усиление, сейчас — программный гард + CI-переменные только тестовые.

### D5. `rozetka-native.ts`: отдельный CI-шаг с БД `_import_test`

Это нативный сценарий импорта, ему нужна отдельная база. В CI создаётся
`CREATE DATABASE ... _import_test` на том же Postgres-service, гард (D4)
запрещает иную цель. Если шаг окажется нестабильным — откат к задокументированному
ручному порядку в `docs/TESTING.md` (разрешено спекой ci-test-discovery).

### D6. Язык и процесс (конфликты источников, фиксируем явно)

- OpenSpec-документы этого change — на русском (прямое указание пользователя),
  хотя §8 аудита требует англоязычной инженерной документации. Решение:
  русские спецификации/дизайн остаются, коммиты — на английском по конвенции
  репозитория; расхождение отмечено в P0-задаче как осознанное.
- Параллельность субагентов: аудит требует ровно 1 последовательного субагента;
  пользователь явно разрешил до 3 параллельно для независимых задач. Решение:
  до 3 параллельно только для непересекающихся по файлам задач (например,
  отдельные группы задач), в остальном — последовательно.
- Фактический объём меньше устаревших черновиков аудита: проверено, что
  `storefront.test.mjs`, `build-smoke.test.mjs`, `frontend/lib/`,
  `calculateShippingCents`, VAT-требований аудита — не существует; соответствующие
  дельты удалены, план строится на подтверждённой фактуре.

## Risks / Trade-offs

- [Jest-набор Medusa замедляет CI] → держать suite небольшой, запускать одним
  шагом параллельно с остальными job; baseline длительности фиксируется в P0.
- [Glob-обнаружение подхватит битый/медленный файл и «покрасит» CI] → перед
  переключением прогнать полный набор локально (задача P1), проблемные файлы —
  в исключения с обоснованием в `docs/TESTING.md`.
- [Двойка Node 20.20.2/24 может дать разное поведение reporters] → обе ветки
  matrix должны выпускать отчёт; при расхождении — fallback-конвертер (D3).
- [Гард D4 не всесилен: опечатка в хосте] → stop-лист расширяем при каждом
  инциденте; секреты в тестах не используем вообще (генерируем).
- [Изменение имён файлов тестов половет внешние ссылки] → переименования только
  с обновлением `docs/TESTING.md` и grep-проверкой ссылок.

## Migration Plan

Порядок совпадает с фазами P0–P4 аудита и группами задач (см. tasks.md):
сначала baseline и каталог (ничего не ломая), затем discovery/CI, затем HTTP-
интеграция, затем усиление изоляции и локализации. Откат каждого шага — revert
коммита; тестовые изменения не влияют на рантайм приложения, поэтому откат
безопасен в любую точку.
