# Design

## Context

YouTrack TB-14 описывает систему избранного (wishlist) для TAMIR Balkan. Реализация уже влита в историю текущей ветки: коммит `d9e958e` (2026-10-27, 31 файл, +631 строка) плюс последующие правки `fix/favorite-icon-background` и `fix/wishlist-header-typography`. Change `wishlist-favorites-system` поздний: его задача — зафиксировать фактический контракт в спеках OpenSpec (capability `wishlist`), сверить реализацию с TB-14, задокументировать осознанные отклонения и закрыть оставшиеся пробелы (браузерный E2E, финальные сверки). Авторитетный источник требований — `TB-14.md` из YouTrack; служебная документация реализации — `docs/WISHLIST.md`.

Существующие контуры, которые избранное только использует, но не меняет: аутентификация покупателя и `LoginDialog` (capability `customer-auth`), каталог и доступность товаров в sales channel (capability `product-catalog`), шапка `ShopHeader`.

## Goals / Non-Goals

**Goals:**
- Единый формальный контракт избранного: UI-поведение, store API, правила хранения — в delta-спеке `wishlist`.
- Подтверждение, что реализация соответствует TB-14 (с учётом задокументированных отклонений), а тестовые контуры из `docs/TESTING-RULES.md` покрывают QA-чеклист TB-14.
- Закрытие пробела браузерного E2E сценариями WD-004 (локальный прогон сейчас; перенос в CI будущего QA-репозитория — отложенный этап).

**Non-Goals:**
- Переписывание таблицы `tamir_customer_favorite` в `customer_favorites` из TB-14 — фактическая схема уже работает, идемпотентна и следует паттерну `tamir_product_url`/отзывов.
- Добавление отдельного переключателя валюты в шапку (TB-14 §2) — валюта остаётся внутри корзины, это решения других change-контурах.
- Изменение модалки входа, корзины, каталога или других capability-спеков.
- Исправление двух предсуществующих падений backend-тестов (`order-email`, `tamir-chat-images`) — они не про избранное.

## Decisions

1. **Таблица `tamir_customer_favorite` вместо `customer_favorites` (отклонение от TB-14).** DDL в `backend/src/utils/wishlist.ts` (`wishlistSchema`), применяется идемпотентно существующим скриптом `backend/src/scripts/setup-reviews.ts` — тот же паттерн, что `tamir_product_url` и отзывы. Кастомный Medusa-модуль и миграции не заводятся: таблица вне ORM-модулей Medusa, доступ через `ContainerRegistrationKeys.PG_CONNECTION` (knex). Ограничение `UNIQUE(customer_id, product_id)` — граница конкурентности (`insert … on conflict ignore`), FK `customer(id)`/`product(id)` с `ON DELETE CASCADE` — каскад физических удалений; мягко удалённые/снятые с публикации товары сохраняются как удаляемая запись. Индекс `(customer_id, created_at DESC, id)` — порядок выдачи «новые первыми».
2. **Владелец только из аутентифицированной сессии.** `wishlistOwner` берёт `auth_context.actor_id` (`actor_type === "customer"`) и проверяет `retrieveCustomer().has_account` / отсутствие `deleted_at` — как в reviews. Любые поля владельца в теле → `400 INVALID_BODY`; `product_id` валидируется регуляркой `^prod_[a-zA-Z0-9]{1,100}$` до обращения к БД (анти-инъекция). Аутентификация подключена конфигом в `backend/src/api/middlewares.ts` (`authenticate("customer", ["bearer","session"])`, sizeLimit 2 kb на POST), обработчики — тонкие route-файлы поверх общего `wishlist-http.ts`.
3. **Контракт ошибок единый в `wishlistFailure`:** `WishlistError` → его статус/код (`LOGIN_REQUIRED` 401, `INVALID_BODY`/`INVALID_PRODUCT` 400, `PRODUCT_NOT_FOUND` 404); pg `23503` → 404; прочее → 503 `WISHLIST_UNAVAILABLE` без утечки SQL/аккаунтов. `Cache-Control: private, no-store` на всех ответах.
4. **Проверка доступности при добавлении** — через `QUERY.graph` по `product` c фильтром `status: "published"` и пересечением `sales_channel_ids` из `publishable_key_context` (`availableFavoriteProduct`); пустой контекст канала → 404. DELETE доступность не требует (недоступное можно удалить).
5. **Клиентское состояние: один `WishlistState` на вкладку через `WishlistProvider`** (`frontend/src/lib/store/wishlist-state.ts`), общий для сердец, счётчика и страницы. `load()` дедуплицируется, повторный клик блокируется `pending`, `ids` применяются после подтверждения сервера, при ошибке сохраняется последнее подтверждённое состояние + флаг ошибки с retry; `dispose()` при смене аккаунта отбрасывает поздние ответы. Обновление при возврате фокуса окна. Никакого `localStorage` — сервер единственный источник.
6. **Гостевой replay в `WishlistProvider`, а не `pendingFavorite` в `LoginDialog` (отклонение от TB-14).** Провайдер хранит намерение (`intent`) + `LoginDialog` из `customer-auth`; после `authenticated && ready` намерение consumes ровно один раз (guard-`ref`). Логика в домене избранного, модалка входа не знает о wishlist. Покрыто компонентным тестом (один POST после входа).
7. **Оформление — брендовый accent вместо жёлтого из TB-14 (отклонение).** Сердца — SVG-экспорт из Figma без изменения геометрии (узлы `209:3591` заливка, `209:3670` контур) как CSS-маски; активное сердце и иконка в шапке окрашиваются `--store-accent` (`#842154`) по решению владельца (2026-10-30, `docs/WISHLIST.md`) вместо `#EAB308`. Область нажатия 44×44, без круглой подложки.
8. **Шапка: Language Switcher → Wishlist → Account → Cart (отклонение от TB-14 §2).** Кнопка избранного (`WishlistLink`) скрыта у гостя, счётчик — бейдж при непустом списке; отдельного currency-селектора нет (валюта в cart preview). Порядок зафиксирован в `ShopHeader.tsx`.
9. **Страница `/wishlist`: клиентская пагинация партиями по 24** (`listProductsByCountry` c `ids`, регион+язык), совпадает с лимитом batch-выборок каталога (PDP related). Недоступные/не готовые к публикации товары — заглушка `wishlist-unavailable` без ссылки, с сердцем-удалением; сбой загрузки каталога не трактуется как недоступность товара. Страница закрыта от индексации, пути локализованы (`/rs/wishlist`, `/en/wishlist`).

## Risks / Trade-offs

- **Браузерный E2E не выполнялся** при реализации: контура QA-автоматизации ещё нет — репозиторий QA-автоматизации будет создан позже (решение владельца 2026-11-16); в работе есть ветка `fix/nexte2e-pdp-wishlist-anchors` (worktree `D:/tamir_balkan/wt/nexte2e-fix`) с Playwright-спеками WD-004. Риск: регрессии визуального/интерактивного поведения не ловятся CI до переноса сценариев в будущий QA-репозиторий → группы E2E в tasks.md (локальный прогон 4.1, отложенный перенос в CI 4.3).
- **DDL таблицы живёт в `setup-reviews.ts`**, а не в медиум-миграциях: если деплой пропустит скрипт, эндпоинты вернут 503 `WISHLIST_UNAVAILABLE` (безопасно, но фича не работает). Митигация: идемпотентный `CREATE TABLE IF NOT EXISTS` уже в потоке деплоя; проверка таблицы на стенде в tasks.md.
- **Интеграционные контуры не запускаются локально без `TEST_REVIEWS_DB_URL`/Medusa-раннера** (guard по дизайну). Риск «не проверено на дев-БД» → задача на прогон DB-контуров в tasks.md с фиксацией результата.
- **Baseline backend-тестов содержит 2 падения не про wishlist** (`order-email` regex `/0,00/`, `tamir-chat-images.test.cjs`); их починка вне этого change — иначе размоет сигнал регрессий избранного.
- **Гостевой replay зависит от порядка «профиль загружен → список загружен → replay»**; изменение очереди загрузок в `AuthWishlistProvider` может задвоить действие. Митигация: consume-guard + компонентный тест «ровно один POST».

## Migration Plan

Изменений схемы в этом change нет: `tamir_customer_favorite` уже создана идемпотентным DDL из `setup-reviews.ts`, выполненным на стенде/в проде до активации релиза. Откат приложения не требует удаления таблицы (данные безвредны). Backfill не нужен — избранное создаётся только действиями покупателя. Если QA-сценарии WD-004 покажут дефект поведения, фикс — обычная правка кода в рамках этого change, без миграций.

## Open Questions

- Контур браузерного E2E (`Ascaronus/Tamir-QA-Automation`) — **закрыто 2026-11-16 решением владельца: репозиторий QA-автоматизации ещё не существует, он будет создан позже.** Поэтому HTTP 404 (проверено при gh-сессии аккаунта `Ascaronus` с classic-токеном со scope `repo`; `GET /user/repos` показывает только `Tamir-Balkan` и `tonirovka`) — не проблема доступа, а отсутствие репозитория. Следствие для плана: интеграция Playwright-сценариев WD-004 в QA-репозиторий откладывается до его появления и фиксируется как отдельный этап (tasks.md 4.3); до этого E2E-проверка идёт по failover — сценарии из ветки `fix/nexte2e-pdp-wishlist-anchors` (worktree `D:/tamir_balkan/wt/nexte2e-fix`, `frontend/e2e/wishlist.e2e.spec.ts`, `wd004-wishlist-pdp-anchors.spec.ts`) прогоняются локально как основа + ручная приёмка по чек-листу TB-14 §7 с протоколом (tasks.md 4.1, 4.2).
- Визуальная сверка Figma-нод `207-3561` после правок типографики шапки — **решение владельца 2026-11-16: «просто макет»** — при расхождении обновляется Figma-макет, а не код (см. tasks.md, группа 1).
