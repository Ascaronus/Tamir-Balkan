# Design

## Context

Задача TB-24: при импорте YAML-фида Rozetka SKU варианта строится из
технического `id` оффера — пары UUID (`skuToken(offer.id)`), в кириллическом фиде превращающейся в
набор цифр. Карточка в Rozetka живёт по артикулу из `<url>` (`.../baf-tmr-1black.html` →
`baf-tmr-1black`), поэтому импорт не узнаёт существующие карточки и заводит дубли.

Проверка по украинскоязычной выгрузке старого каталога (2 444 681 Б): **821 оффер, 322
уникальных артикула, дублей артикулов нет**
(один товар = один цвет, цвет зашит в артикул: `-siri`, `-pisochni`), размеры лежат **только** в
`<param name="Размер">`, других размерных параметров в фиде нет. Формула `АРТИКУЛ-РАЗМЕР` даёт
821 уникальный SKU из 821 офферов; чистый артикул — только 322 (многоразмерные товары сталкиваются).

Импорт имеет два пути, которые не должны разъехаться: админский `POST /admin/rozetka/import`
(SKU считается в снимке предпросмотра `src/utils/rozetka-preview.ts`, пишется в
`src/utils/rozetka-admin.ts`) и CLI `npm --prefix backend run import:rozetka:xml`
(`src/scripts/import-rozetka-xml.ts`).

## Decisions

1. **SKU = `АРТИКУЛ[-РАЗМЕР]` (выбранная формула).** Общие хелперы в `src/utils/rozetka.ts`:
   `articleFromOfferUrl` (последний сегмент `<url>` без `.html`/`.htm`, не-латиница → пустая
   строка), `skuToken` (NFKD, всё кроме `[A-Za-z0-9]` → `-`, сжатие, верхний регистр), `isOneSize`
   (пусто, `One size`, `one_size`, `OS`, `edini`, `univer`, «без размера», «один размер»…),
   `legacySkuFromOffer` (прежняя формула), `rozetkaSku(offer, size)` — точка сборки. Оба пути
   импорта вызывают только `rozetkaSku`. Отклонённые альтернативы:
   - *оставить `offer_id`* — SKU бессмысленен для человека и не совпадает с артикулом Rozetka,
     дубли карточек сохраняются;
   - *артикул + цвет* — отдельного машинного параметра цвета в фиде нет, цвет уже внутри артикула,
     отдельного смысла надстройка не имеет;
   - *только артикул* — конфликтует на многоразмерных товарах (322 SKU на 821 оффер).
2. **Fallback, а не транслитерация.** Если артикул не латиницей (кириллица) или `<url>` нет, SKU
   остаётся прежним (`skuToken(offer.id)`): транслитерация двух разных кириллических слов могла бы
   схлопнуться в один SKU — риск тише, чем падение импорта или ложный матч.
3. **Мета варианта для трассировки.** В `metadata` пишутся `rozetka_offer_id`, `rozetka_article`
   (артикул из URL) и `rozetka_legacy_sku` (прежний SKU из offer id); в `SourceVariant` добавлены
   `article?`/`legacy_sku?`. Это даёт скрипту ретро-фиксации и повторным импортам способ сверить
   старые карточки, не угадывая по handle/заголовку.

## Risks / Trade-offs

- **Коллизия SKU.** Формула меняет ключ сопоставления вариантов и ключ поиска инвентарного
  элемента, поэтому новые SKU обязаны быть уникальны. Уникальность проверена по
  украинскоязычной выгрузке старого каталога: 821/821; на рабочем фиде — 22/22. Митигации:
  валидация черновика админки (`draftErrors`) и проверка занятости SKU перед
  записью с ответом `409` «SKU … уже используется другим вариантом»
  (`src/utils/rozetka-admin.ts:171`). В CLI карта остатков `skuToStock`
  (`src/scripts/import-rozetka-xml.ts:571`) ключуется SKU, поэтому коллизия двух офферов
  слила бы их остатки (побеждает последний) — при 0 коллизий в обоих выгрузках отдельная защита в CLI
  не добавлялась, при появлении коллизий в фиде их видно в отчёте импорта.
- **Ключ сверки остатков при полном импорте.** `missingSourceInventory`
  (`src/utils/import-scope.ts:8-9`) тоже сравнивает `sku` варианта с множеством SKU фида и в
  режиме `ROZETKA_IMPORT_MODE=full` обнуляет уровни склада у «отсутствующих» вариантов
  (`src/scripts/import-rozetka-xml.ts:835-849`). Пока база и фид используют одну формулу,
  ретро-фиксация этот механизм не ломает; если прогнать `full`-импорт до ретро-фиксации, остатки
  старых карточек будут обнулены. Порядок «ретро-фиксация → импорт» обязателен.
- **Разовый конфликт предпросмотра в админке.** `fingerprint` товара считается как
  `digest(JSON.stringify(product))` (`src/utils/rozetka-preview.ts:113`), а в снимок добавлены
  `article`/`legacy_sku`, поэтому сохранённые ранее черновики не совпадут с новым снимком и
  импорт ответит `409` «Товар в XML изменился…». Это ожидаемое одноразовое состояние: кнопка
  «Принять текущие данные» на странице админки обновляет черновик.
- **Разрыв преемственности старого импорта.** Без ретро-скрипта уже импортированные карточки
  (SKU из offer id) перестают узнаваться новым импортом → риск дублей после релиза. Митигация —
  обязательный прогон `fix:rozetka:sku` (см. Migration Plan) до включения нового импорта.
- **Повторный импорт до ретро-фиксации** даст пару «старый вариант + новый вариант» у одной
  карточки; принято осознанно как переходное состояние, закрывается скриптом.

## Migration Plan

`npm --prefix backend run fix:rozetka:sku` — скрипт в стиле `normalize-rozetka-products`:
dry-run по умолчанию, применение только через `ROZETKA_SKU_FIX_APPLY=true`, под `withImportLock`,
идемпотентен. Порядок: загрузить свежий фид → по `rozetka_offer_id` (и `rozetka_legacy_sku` как
вторичному ключу) найти уже импортированные варианты → вычислить новый SKU через `rozetkaSku` →
переименовать `sku` варианта и `sku` его инвентарного элемента. Остатки не теряются, потому что
уровни склада привязаны к инвентарному элементу Medusa (`inventory_item_id`), а не к строке SKU:
обновляется только `sku` элемента, связи `inventory_level` остаются на месте. Офферы, отсутствующие
в свежем фиде, скрипт не трогает; конфликты занятых SKU не применяются и выводятся в отчёт.
Откат: SKU не имеет семантики для Medusa, обратное переименование возможно тем же скриптом при
возврате старой формулы — данных миграция не удаляет.

## Open Questions

- Релиз без эмбарго: между выкаткой новой формулы и прогоном `fix:rozetka:sku` админский импорт
  заводит карточки со старыми SKU рядом с новыми. Нужен ли явный тумблер, блокирующий импорт до
  ретро-фиксации, или достаточно порядка деплоя (скрипт прогоняется сразу после выкатки, до
  первого импорта)?
- Нужен ли пересчёт SKU у карточек, удалённых из фида (их офферы не находятся в свежем фиде,
  скрипт их пропускает): оставлять прежний UUID-SKU или чинить по сохранённому `rozetka_article`.
