# Выпуск TAMIR на VPS

Актуально на 2 ноября 2026. Рабочий checkout: `/root/tamir_balkan`; PM2-процессы: `tamir-backend`, `tamir-frontend`. Приложения работают из отдельных каталогов релизов, а не обязательно из checkout.

## Перед деплоем: секреты вне Git

Пароли и приватные ключи приложения хранятся на VPS и в защищённой резервной копии владельца. В репозиторий попадают только шаблоны. См. [SECRETS.md](docs/SECRETS.md): перед первым выпуском этой конфигурации заполните локальное окружение, согласуйте его с окружением PM2 и проверьте JWT/COOKIE. Push в `main` ведёт себя иначе: он проверяется CI и автоматически разворачивается на staging
([STAGING.md](docs/STAGING.md)), а на прод попадает только то, что выпускают вручную. Не
объединяйте изменение до подготовки VPS. Простое изменение Compose не меняет пароль существующей БД.

## Основной способ: GitHub Actions

1. Подготовить PR в `main`, проверить diff и результат `Verify storefront and backend`.
2. После merge CI на push в `main` автоматически разворачивает этот коммит на staging —
   **Deploy to Staging** (`test.tamir.rs` / `test-api.tamir.rs`, см.
   [STAGING.md](docs/STAGING.md)). Прод из этого не следует: решение о выпуске принимает человек.
3. Выпустить прод: Actions → **Deploy TAMIR** → Run workflow из ветки `main` → указать `sha`
   (40 hex) коммита, который уже прошёл Verify в `main`. Обычно это HEAD `main`, но это может быть
   и более старый коммит `main` — например, если свежие коммиты ещё не проверены на стенде.
   Job деплоя привязан к окружению `production`: в настройках репозитория (Settings → Environments)
   для него можно включить required reviewers и branch policy — тогда деплой требует отдельного
   подтверждения. Автоматических триггеров у `deploy.yml` нет.
4. Проверить завершение deploy и публичные страницы.

В заголовке нового запуска **Deploy TAMIR · `<sha>`** показан именно выбранный `inputs.sha`.
Коммит рядом с веткой workflow может быть другим: это версия самого workflow, а не обязательно
выпускаемого приложения. Для исправления чата нужен коммит, содержащий PR #112; повторный выпуск
`739ae266fb21dbe28ffbebed707d920071f20a75` исправления не содержит.

Workflow использует ограниченный SSH-доступ `tamir-deploy` и команду `deploy`, secrets `VPS_HOST`, `VPS_PORT`, `VPS_SSH_KEY`, `VPS_KNOWN_HOSTS`, проверку host key. Конкурентные выпуски сериализованы. Перед тем как что-либо отправить на сервер, workflow сверяет введённый `sha` с GitHub API: `compare main...sha` обязан вернуть `behind` (коммит входит в историю `main`) или `identical`, а прогоны `verify.yml` на этом коммите в `main` (события `push`/`workflow_dispatch`) — быть `completed` с conclusion `success`/`neutral`/`skipped`. Иначе запуск падает на первом же шаге, и до VPS ничего не доходит. Deploy выпускает ровно тот коммит, который указан в `sha`: значение проверяется на формат из 40 hex-символов и передаётся команде `deploy` обязательным аргументом; `deploy-vps.sh` без него отказывается запускаться. Обёртка `deploy` на VPS обязана пробрасывать аргументы (`"$@"`) в `scripts/deploy-vps.sh`. Всё равно проверяйте SHA в имени активированного релиза.

### Staging перед продом

Тот же коммит сначала проверяется на стенде автоматически: push в `main` → `Verify` →
**Deploy to Staging** (self-hosted runner на машине владельца, `test.tamir.rs` /
`test-api.tamir.rs`). Стенд мигрирует базу всегда, прод — нет, поэтому миграции из PR обязаны
отработаться на стенде до прод-выпуска. Стенд не имеет доступа к прод-БД, прод-Redis, прод-почте
и прод-платежам; данные на нём — анонимизированная копия прода. Подробности, скрипты и типовые
сбои: [STAGING.md](docs/STAGING.md).

Важная тонкость: `Verify` не запускается на push, в котором менялись только `docs/**`,
`openspec/**` или любые `.md` (`paths-ignore` в `verify.yml`). Такой merge в `main` не поднимает
и staging — чтобы принудительно развернуть стенд, запустите **Deploy to Staging** вручную с тем же
SHA. На PR фильтр не действует: required-чеки защищённого `main` приходят по любому PR.

### known_hosts и HostKeyAlias

Workflow подключается к `tamir-deploy@$VPS_HOST` с `StrictHostKeyChecking=yes`, `HostKeyAlias=tamir-vps` (`.github/workflows/deploy.yml`) и известными хостами из secret `VPS_KNOWN_HOSTS`. При `HostKeyAlias` ssh сверяет ключ по имени алиаса, поэтому запись в секрете обязана начинаться с `tamir-vps`, а не с адреса или домена сервера; запись вида `<адрес> ssh-ed25519 ...` не сработает и выпуск упадёт на проверке host key.

Запись генерируют так (порт берут из `VPS_PORT`, адрес — из `VPS_HOST`), затем отпечаток обязательно сверяют независимым каналом, например выводом `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` на самом сервере:

```bash
ssh-keyscan -t ed25519 -p <VPS_PORT> <адрес VPS> | sed 's/^[^ ]*/tamir-vps/'
```

В secret `VPS_KNOWN_HOSTS` сохраняют строку целиком (алиас, тип ключа, base64, комментарий). При смене host key VPS (переустановка, перевыпуск ключа) секрет обновляют той же командой до ближайшего выпуска.

## Что делает скрипт

`scripts/deploy-vps.sh`:

1. Проверяет утилиты, отсутствие локальных изменений tracked-файлов и блокировку `/root/tamir-deploy.lock`.
2. Требует обязательным аргументом точный 40-hex SHA проверяемого коммита (при отсутствии, неверном формате, неизвестном объекте или отсутствии коммита в `origin/main` выпуск прекращается), получает `origin/main`, проверяет допустимый fast-forward, создаёт `/root/tamir-releases/<UTC>-<SHA>`.
3. Сохраняет в `/root/tamir-backups/<UTC>-<SHA>` PostgreSQL custom dump, env, прежнюю PM2-конфигурацию и архивы public/private media.
4. Для frontend закрепляет `NEXT_PUBLIC_SITE_URL=https://tamir.rs` в новой PM2-конфигурации до сборки и использует её при сборке и запуске. Устанавливает зависимости и собирает backend/frontend в новом каталоге; выполняет frontend lint/tests и конфигурационный preflight CAPTCHA/SMTP. Старое окружение в бэкапе и исходные env-файлы сохраняются.
5. Сохраняет доступ к существующим media через symlink. Выполняет `setup-reviews.ts`, проверку SMTP без отправки письма и `setup-decimal-attributes.ts`.
6. Передаёт релиз `activate-release.sh` **из выбранного каталога релиза**: переключает два PM2-процесса, проверяет health/robots/sitemap и Origin чата, сохраняет PM2. Проверка чата делает `POST /api/chat/config` с пустым JSON без cookies и ID диалога: для публичных origin ожидает `404 CHAT_NOT_FOUND` от backend, для стороннего — `403 INVALID_ORIGIN` от frontend. Проверяются loopback, `https://tamir.rs` и `https://www.tamir.rs`; диалоги, сообщения и уведомления Telegram не создаются (затрагивается только счётчик rate limit). При сбое активации процессы откатываются на прежний релиз, а checkout `main` на VPS остаётся на предыдущем коммите. Fast-forward checkout выполняется только после успешной активации; короткий простой витрины при переключении PM2 считается принятым (fork-режим npm-скриптов не поддерживает `pm2 reload`).
7. Уже после активации выполняет `normalize-rozetka-products.ts` с apply и `prepare-english-store.ts`: native-переводы, адреса и опции.

Скрипт не запускает общую `medusa db:migrate` автоматически. При добавлении новых Medusa-миграций нужен отдельный план их применения и совместимости. Текущие пользовательские таблицы/дробные поля подготавливаются явно указанными скриптами.

Для deploy необходимы `git`, `npm`, `node`, `pm2`, `pg_dump`, `curl`, `tar`, `flock`, готовое окружение и по одному online-процессу каждого приложения. Это обновление существующего сервера, не установщик чистого VPS.

## Ручной запуск через SSH

```bash
ssh root@tamir.rs
cd /root/tamir_balkan
git fetch origin main
git show origin/main:scripts/deploy-vps.sh > /tmp/tamir-deploy.sh
bash /tmp/tamir-deploy.sh "$(git rev-parse origin/main)"
```

Ручной выпуск закрепляет SHA явно: без аргумента из 40 hex-символов скрипт остановится. Здесь оператор сознательно выбирает текущий `origin/main` сам; workflow прод-выпуска берёт SHA, который оператор же и указал при запуске, предварительно проверив его по GitHub API.

При первом выпуске изменений самого `deploy-vps.sh` проверьте установленную SSH-обёртку:
она должна запускать версию скрипта выбранного SHA, а не старую копию из рабочего checkout.
Код обёртки не хранится в этом репозитории. Если она запускает старую копию, используйте ручной
путь выше с SHA, прошедшим Verify, и извлеките скрипт из **этого же SHA**. Иначе новые проверки
деплоя начнут действовать только после обновления checkout; зелёный workflow сам по себе
не подтверждает, что исполнилась новая версия deploy-скрипта.

Скрипт сам переносит checkout к выбранному коммиту. Не используйте `scp` поверх активного релиза, удаление работающего `.next`, `fuser -k` или ручной `npm start` как штатный способ выпуска.

## Конфигурация и данные

Окружение редактируется в исходном каталоге и согласуется с существующими переменными PM2: [ENVIRONMENT.md](docs/ENVIRONMENT.md). Скрипт запуска backend в production стартует из `.medusa/server`; простая замена `.env` в другом каталоге не меняет уже работающий процесс.

Не удаляйте старые релизы, пока не проверили `media-paths.json` и реальные цели ссылок `static`/`private-static`: новый релиз может использовать принадлежащие им фотографии. Резервная копия содержит секреты и данные покупателей; храните её вне Git и публичной раздачи.

## Диагностика

```bash
pm2 list
pm2 describe tamir-backend
pm2 describe tamir-frontend
pm2 logs tamir-backend --lines 100 --nostream
pm2 logs tamir-frontend --lines 100 --nostream
curl -fsS https://api.tamir.rs/health
curl -I https://tamir.rs/rs
curl -I https://tamir.rs/en
curl -fsS https://tamir.rs/robots.txt
curl -fsS https://tamir.rs/sitemap.xml
```

Ожидается: `/rs`, `/en` — 200, `/` — временный 307 по языку; старый `/rs/cart` — 308 на `/rs/korpa`. В sitemap должны быть главные обеих локалей, готовые товары и непустые категории. Проверяйте реальный товар, выбор варианта, корзину, страницу входа и импорт без создания лишних заказов.

PostgreSQL здесь может работать в Docker, поэтому отсутствие `postgresql.service` в systemd не означает отсутствие базы:

```bash
cd /root/tamir_balkan
docker compose ps -a
docker compose logs --tail=100 postgres
```

Сначала изучите ошибку. Не удаляйте том `postgres_data` и не запускайте `down -v` для восстановления рабочей базы.

## Ротация бэкапов

Каждый релиз создаёт бэкап в `/root/tamir-backups/<UTC>-<sha>`. Скрипт деплоя
хранит **последние 14** релизных бэкапов и после успешной активации релиза удаляет
более старые; файлы, созданные вручную (не по шаблону имени релизной папки), не
трогаются.

## Ошибки и откат

- До активации: старые процессы продолжают работать; используйте путь резервной копии из лога. Отдельные подготовительные изменения БД могли уже выполниться.
- При ошибке активации/health: `activate-release.sh` пытается восстановить предыдущую PM2-конфигурацию и сообщает результат.
- После активации: ошибка нормализации/переводов может завершить workflow неуспешно при уже работающей новой версии. Автоматического отката этого этапа нет. Проверьте логи и исправьте причину перед повтором.
- Откат процессов не откатывает БД. Восстановление `database.dump` — отдельная операция с риском потери новых заказов; сначала проверьте дамп на отдельной базе и выберите точку восстановления.

Не повторяйте деплой параллельно с импортом/ремонтом данных. Автоматический `prepare-english-store.ts` может обращаться к Google для недостающих переводов; он сохраняет заполненный контент по правилам [LOCALIZATION.md](docs/LOCALIZATION.md).
